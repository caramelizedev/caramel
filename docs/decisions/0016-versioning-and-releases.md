# ADR 0016: One version serves the repository, applications pin a release as a shard, and each release keeps stated compatibility promises

Date: 2026-09-28

Status: accepted.

## Context

Caramel needs releases that applications can pin, upgrade and install side by side:

- One version number must serve the framework, Latte and the shard, and compatibility between Frappé, Latte and its state must be explicit.
- Latte is one per user on the default ports (one daemon, one PostgreSQL cluster, one CA, one resolver, one relay), while several Caramel versions can be installed at once. Another state root (a check's, or a second user's) runs on ports of its own and gets no resolver or relay, and a Latte whose port is held refuses to start that service and names the port's owner before starting anything (`site#c-local-latte`).
- A copied framework and a thick generated entry point would drift from the release an application pins.
- `bin/frappe` and `bin/latte` find OpenSSL through an absolute rpath into the builder's toolchain, so they cannot run on another machine ([ADR 0001](0001-toolchain-and-setup.md)).

## Decision

What a user of a release relies on is stated on the website ([site.html](../../website/source/site.html)), in the sections cited below by anchor, and in the doc comments under [src/caramel](../../src/caramel), [src/latte](../../src/latte) and [src/frappe](../../src/frappe). The release tool is [scripts/release](../../scripts/release), and `CONTRIBUTING.md` repeats the promises for contributors. This record states what was chosen.

1. **One version serves the repository.** The public repository `github.com/caramelizedev/caramel` tags a release `vX.Y.Z` (`Caramel::REPOSITORY`), by semantic versioning. A pre-release is `X.Y.Z-rc.N` and is tagged by hand; `scripts/release` cuts final releases. During 0.x a minor release may break compatibility, and a patch release never does. The version is written only in `shard.yml`: `Caramel::VERSION` is generated from it, and so are `Latte.app`'s bundle versions, which `scripts/build-latte-menu` writes.
2. **Latte's control API is versioned, and each side names its window.** Latte serves the versions in `Latte::ControlAPI::VERSIONS` and answers any other with `unsupported_api`, its release and its window; it also reports its release and window in `/v1/status`. Each Frappé states the one version it needs (`LatteClient::API_VERSION`) and, on a mismatch, names the release that fixes it. `latte version` prints the release and the window (`site#c-commands-latte`).
3. **Latte's state formats migrate forward, and a release refuses a newer format.** State formats migrate forward when Latte starts; the first new format adds its forward migration. Latte's registry, `installations.json` and the trust receipt refuse a newer format, naming the file and the format this release reads (`Latte::StateFormat`); the Swift toolchain installer refuses a newer receipt the same way. Choosing which Latte runs is not refusing: when `installations.json` is unreadable there, this release's own Latte runs (`InstalledReleases.newer_latte`).
4. **A PostgreSQL major bump ships a `pg_upgrade` step.** The previous major's binaries are kept until that step has run. Each major has its own cluster directory (`Paths#postgres_data`), and Latte refuses to start an empty cluster beside another major's data (`Postgres#refuse_other_major_cluster!`). Latte adopts a postmaster that another toolchain's build of the major started on the cluster's directory, identified by the private PID file, owner, start time and data directory.
5. **Framework migrations are only appended, never edited.** `scripts/release` refuses to tag when a migration the last release shipped was edited or removed, or a new one sorts before it.
6. **Latte's CA is never replaced silently.** `site#c-local-setup` states what `latte trust install` refuses.
7. **The resolver, relay and plist belong to the newest installed release.** `frappe doctor` asks the newest installed release and reports a resolver, relay or plist that differs from that release's, with the commands that replace it. It prints `prepare` then `sudo … apply` when nothing is installed, or `prepare`, `sudo … uninstall` and `sudo … apply` to replace another release's integration, which `apply` alone refuses. `install-local-integration status` compares them without sudo (`site#c-local-setup`, `site#c-local-releases`).
8. **An application depends on the framework as a shard.** A generated application declares `caramel: github: caramelizedev/caramel, version: "~> X.Y.Z"`, and its `shard.lock` pins the release's commit, which Shards checks out. `CARAMEL_REPOSITORY` substitutes a git repository for GitHub; that entry pins the release by tag alone. A checkout that is not a git checkout of its release tag without tracked changes (an unreleased checkout, or a source archive) generates applications with a `path:` dependency on itself; untracked files, such as an application generated inside a release clone, do not make a release unreleased (`NewProject#dependency`). `vendor/caramel/`, `snapshot.json` and `.caramel-version` do not exist: Frappé reads the pinned version from `shard.lock` (`site#c-local-releases`).
9. **Every git dependency is locked to the commit its tag pointed at.** The lock uses Shards' own pin form, which Shards checks out whatever the tag points at now and records in `lib/.shards.info`; the form, the `scripts/check shard-pins` refusal and the generated application's lock are in `site#c-releases-dependencies`. `scripts/shards` refuses an install that put a pinned shard at another commit. A generated application locks Caramel's commit and copies the framework's entries. Crystalline's dependencies are pinned the same way, from `tools/editor-darwin-arm64.json` (`EditorTools#pin_crystalline_dependencies`). `shards update` strips the pins, so a dependency is updated by writing its tag's commit into the lock by hand.
10. **A release's framework changes only with `shard.lock`.** `frappe dev` watches `shard.lock` (`site#c-local-dev`). A `path:` dependency's sources are hashed into every build's fingerprint but not watched; `DevFiles#framework_source` says what to do after editing that checkout.
11. **Frappé installs the version a project pins.** `frappe installations install VERSION` clones the tag, installs its toolchain, builds it with that release's own `scripts/build-release` and registers it (`Release`, `site#c-local-releases`); releases through 0.3.0 have no build script and are built with fixed steps. Installing a registered release again builds what it lacks, such as the linter, and `frappe doctor` names that command. When a project pins a version that is not installed, Frappé offers to install it on a terminal, or prints that command to agents and pipes. `frappe installations register` remains for contributors' checkouts.
12. **One Latte runs: the newest installed.** On-demand start, the login item and the `~/.local/bin` launchers all run the newest installed release's Latte, and `latte daemon` hands over to the newest installed release's built `latte` (`site#c-local-releases`). How Latte starts on demand and at login is in [ADR 0012](0012-latte.md), and what the launchers are in [ADR 0001](0001-toolchain-and-setup.md). Older releases' Frappé use that Latte through the API window. A Frappé that needs a newer API than the running Latte names the release to install.
13. **Releases are cut by `scripts/release`, written in Crystal.** It derives the next version from the Conventional Commits since the last tag: a fix is a patch and a feature is a minor; a breaking change is a minor during 0.x. It writes `CHANGELOG.md` from those commits plus hand-written upgrade notes (`CHANGELOG.md` holds the Unreleased notes), sets the version in `shard.yml`, and creates an annotated tag only after the full check suite passes. It refuses a version that `website/source/site.html` does not name; the check suite it runs includes `scripts/check website`, which builds and checks that edition with Node.js 22 or newer. Pushing the tag and publishing the GitHub release stay manual.
14. **Releases are source-only until signing.** A release is a tag and its source archive; users build with `scripts/install-toolchain` and the build scripts, or with `frappe installations install`. Prebuilt, notarized binaries wait for an Apple Developer ID, before 1.0. They also need three things: OpenSSL shipped beside the binaries with an `@executable_path`-relative rpath, or linked statically; `SMAppService` for the login item and the port relay; and a signed release manifest that the Swift installer verifies with CryptoKit.
15. **A removal is deprecated first.** Even in 0.x, a removal is preceded by one release that warns and names the replacement; `CONTRIBUTING.md` states the rule. A command carries `deprecated:` in the command table (`Command#deprecated`), and framework APIs use Crystal's `@[Deprecated]`. Support windows are published at 1.0. A change whose warning cannot reach applications, such as a compile-time narrowing in the framework that Crystal reports inside `lib/`, where warnings are hidden, ships as a breaking change in a minor release without a deprecation release; the record of the rule it changes says why.
16. **The version is visible to agents.** `frappe agent-manifest` prints `VERSION:`, `DOCS:` and `GUIDES:` lines after its first line (`site#c-agents-orient`). The documentation for each release is the tagged tree on GitHub, and `GUIDES:` names the Markdown index of that release's guides, `https://caramelize.dev/docs/X.Y.Z/llms.txt`.
17. **The generated application is thin.** Its behaviour lives in the framework: the application's main is one call, `Caramel.run(App)`, and its spec helper's configuration is `Corretto.configure(App)`. `config/database.yml` does not exist, because `Caramel::Database.url` knows Frappé's variables.

## Reasons

- Rejected: copying the framework into each app, because Rails 2's `vendor/rails` copies were edited and drifted until Bundler and a lockfile replaced them.
- A project's pin should select, and if necessary fetch, its tools, as `bin/rails`, `artisan`, mix tasks and Go 1.21's `go.mod` toolchain line do.
- Generated code becomes code that users upgrade by hand (Laravel 11 cut its skeleton for this reason), so the generated app stays thin. With its behaviour in the framework, a framework upgrade upgrades it.
- A single local environment should be its own product and own its binaries: Laravel Herd does, and Valet broke when Homebrew upgraded its packages.
- Postgres.app keeps a data directory per PostgreSQL major version, and `pg_upgrade` needs the old and new binaries at once.
- A database is never lost across an upgrade, and the CA is never replaced silently.
- Rails and Django warn for at least one release before removing a feature.
- The release tool itself is native; only the website check runs Node, which the website's build already needs.
- Deferred: mechanical upgrades. Publishing the diff between apps generated by consecutive releases, and a `frappe upgrade` command that applies what it can, are wanted eventually but not built.
