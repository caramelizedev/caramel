# @@TITLE@@

A Crystal browser application built with Caramel @@VERSION@@, PostgreSQL and locally bundled htmx 4.

```sh
frappe setup  # after cloning; creates fresh private local credentials and applies migrations
frappe dev    # compiles, watches, and opens your named HTTPS project
```

Create your first feature:

```sh
frappe make resource Book title:string author:string
frappe migrate
frappe corretto
```

Routes live in `config/routes.cr`, actions in `app/actions/`, views in `app/views/`, SugarORM schemas in `app/models/`, changesets in `app/changesets/`, other application code in `app/`, and database changes in `db/migrations/`. Each action declares a `contract do ... end` of typed fields; route parameters must match contract fields, and the build fails otherwise. `frappe routes` lists every route with its contract. Actions answer browsers with HTML and clients sending `Accept: application/json` with JSON. `redirect_to(path)` navigates within the application; `redirect_external(url)` sends the browser to another site and accepts only an absolute http or https URL without credentials. Views are Blueprint classes, such as `App::Views::Books::Show < App::ApplicationView`: typed inputs in `initialize`, markup as Crystal in `private def blueprint`, and every text and attribute value escaped unless it is a `Caramel::HTML::Safe`. An action renders one with `page "Book", Views::Books::Show.new(book)`. Register client components with `CaramelIslands.define("Name", (element, props) => ...)` in `app/assets/javascript/app.js` and render them in a view with `island "Name", props`. Generated files are yours to edit. Source assets live in `app/assets/`; Frappé publishes them into `public/assets/`. Only `public/` is served directly.

A view is a class under `app/views/` whose `private def blueprint` writes markup with element methods. An element takes attributes and a block, and the text the block returns is escaped: `h1 { @book.title }`. Attribute values are escaped too. Underscores in attribute names become dashes (`hx_post:` writes `hx-post`), and a quoted name keeps other characters (`"hx-swap:inherited": "innerMorph"`). `plain "text"` writes escaped text beside other elements, `render Views::Books::Card.new(book)` writes a child view in place, `raw value` writes a `Caramel::HTML::Safe` value unescaped, and `island "Name", props` writes a client island. A layout receives the rendered page and writes it with `raw page.html`. For a fragment too small for a class, an action can build it inline: `morph "#count", with: markup { span { count.to_s } }`.

Run `frappe --help` for implemented commands, or `frappe COMMAND --help` for one command's syntax. Invalid input exits 1 and prints the intended syntax. `frappe seed` executes `db/seeds.cr` without resetting data. The optional `frappe add auth` feature is still being built.

`frappe check` type-checks the whole application without code generation. It prints each compiler error with its file, source line, caret and remediation, or MRDP lines for coding agents (`--agent`, or when output is piped; `--human` forces the terminal layout). A route parameter missing from its contract comes with a `PATCH:` that adds the field, and an association used without `.preload` is reported as `N_PLUS_ONE`. `frappe agent-manifest` prints every command and the MRDP grammar. `frappe routes books` lists only the routes whose method, path or action contains `books`. `frappe expand app/actions/books/show.cr:3:5` prints the Crystal that the macro call at that line and column generates. `frappe db branch create try_isbn` clones the development database and prints the branch's connection URL; `frappe dev --branch try_isbn` runs the app against that branch, and `frappe db branch list` and `frappe db branch delete try_isbn` manage branches.

`frappe lint` checks the code against Caramel's RFC-0008 rule set in `.ameba.yml`: descriptive names, no service nouns such as `InvitationService`, short blocks, positive conditions, and actions small enough to read as one thought. Like `frappe check`, it prints MRDP for agents. It never rewrites code; `frappe format` formats the Crystal files.

Quantities read as what they measure (RFC-0008 §2.3). Crystal gives `48.hours` and `3.days.from_now`; Caramel adds `at_midnight`, as in `3.days.from_now.at_midnight`, the start of that day in its time zone, and byte sizes such as `50.gigabytes`, an `Int64` count in binary multiples: a kilobyte is 1024 bytes.

Schemas are immutable rows; every write goes through a changeset. `App::Book.create(title: "Dune")` and `book.update(title: "Dune")` build `App::Book::CreateChangeset`/`UpdateChangeset`, validate, write, and return the changeset: check `saved?`, then use `record` or show `errors`. Read with `App::Book.query.where(author: "Frank Herbert").order_by(:id, :desc).limit(20).to_a` or `App::Book.query.find(id)`. When the application serves, `SugarORM::Repo.database` is its connection pool; in specs Corretto binds each example's connection instead. In a changeset's `validate`, `cs.unique_constraint(:email)` turns a unique-index violation into an error on that field instead of a failed request, and `cs.validate_url(:original_url)` accepts only the URLs `redirect_external` accepts, so a saved link can be followed. For SQL the query API does not cover, `SugarORM.sql("UPDATE links SET click_count = click_count + 1 WHERE short_code = $1 RETURNING original_url", code, as: {original_url: String})` returns typed rows, and `SugarORM.sql_exec(query, args...)` returns the number of rows it changed.

Background jobs live in `app/jobs/`: `struct SendReceipt < Caramel::ColdBrew::Job` declares `queue "mailers"` (default `default`), typed `param order_id : Int64` fields, optional `retry_on Stripe::RateLimitError, attempts: 5, backoff: :exponential, base: 2.seconds`, and `def perform`. `SendReceipt.enqueue(order_id: order.id, run_at: 10.minutes.from_now, priority: 5)` writes the job through the current connection, so inside `SugarORM::Repo.transaction` it commits or rolls back with your data; the job's own writes and its completion also commit together. Without a matching `retry_on` a job runs at most 3 times with exponential backoff from 1 second, then keeps `failed_at` and `last_error`. `serve` runs workers for `CARAMEL_WORKER_QUEUES` (comma-separated, default `default`) with `CARAMEL_WORKER_CONCURRENCY` fibers each (default 4), a maintenance fiber, and every `Caramel::ColdBrew.every(1.hour, "nightly-cleanup") { ... }` schedule, which one process runs per period; SIGTERM lets in-flight jobs finish. Specs run no workers: call `Caramel::ColdBrew.drain_queue!(db, "default")` to run due jobs synchronously. `Caramel::ColdBrew.publish("board_1", payload)` notifies on commit, and an SSE action streams `Caramel::ColdBrew.subscribe("board_1") { |updates| ... }` with `Caramel::SSE.write(io, event: "BoardUpdated", data: updates.receive)`. `Caramel::Cache.fetch("key", expires_in: 5.minutes) { ... }` caches strings in an UNLOGGED table. Framework tables start with `caramel_` and come from `Caramel::ColdBrew::MIGRATIONS`, which `App::MIGRATIONS` starts with.

Specs use Corretto and never mocks: `frappe corretto [SPEC_PATHS...] [--concurrency=N]` migrates the spec database once, clones one Latte worker database per worker from it, and runs the spec files round-robin in parallel. Every example runs inside a savepoint that is rolled back afterwards; `Corretto.session do |client, db| ... end` yields an in-process client (cookie jar, automatic CSRF, `get`/`post`/`put`/`patch`/`delete`, `follow_redirect`, `sign_in(user)`) and the example's connection. Assert with `have_status`, `render_page`, `render_partial("#target", swap: "innerMorph")`, `redirect_to`, `have_header` and `db.should have_row(App::Book, title: "Dune")`. Tag an example `catalog` when it must run DDL; it runs unwrapped and its worker database is recloned afterwards. Third-party HTTP sent through `Caramel::Outbound` is answered by `Corretto.stub_wire(url, method: "POST").to_return(status: 200, fixture: "stripe/customer.json")` from `spec/fixtures/wire/`; unstubbed requests get 502. `frappe corretto` refuses specs that call mocking APIs such as `allow(` or `double(`.

Schemas in `app/models/` declare your tables. After changing one, `frappe db diff --name add_isbn` clones the development database into a disposable Latte branch, derives the migration, checks it against the zero-lock linter, proves it on the branch, and writes `db/migrations/<UTC timestamp>_add_isbn.cr`. Index changes on existing tables go into a separate `_concurrently` migration that runs outside a transaction. Risky changes halt with a remediation: a NOT NULL field without a default, SET NOT NULL, a type change, or a column no field declares. Rename a field with `renamed_from: :old_name`, and drop a column with `drop_column :old_name`. `frappe migrate` lints and applies pending migrations, then warns about remaining drift between the schema and the database. In development only, `--dev-override` on either command turns halts and lint violations into warnings; test and production always refuse them.

`frappe dev` watches Crystal and configuration with kernel file events. Each source change is type-checked first: a type error shows its diagnostic page at the same HTTPS address right away and prints `Type check failed in N ms`, without waiting for a native build. A passing check prints `Type check passed in N ms` and continues with the full build. Broken builds recover when you save a fix. CSS/JavaScript changes refresh without compilation. Pending migrations require an explicit `frappe migrate`; dev resumes after they are applied. Ctrl-C stops this project's app and watcher while leaving shared services and other projects running. `--no-open` suppresses browser launch and still requires working named, trusted HTTPS. Use `frappe doctor` if local DNS or trust needs repair.

Zed support is optional. Run `frappe lsp install` once per Caramel installation (it pins and builds the Crystal language servers without Homebrew). Trust the project when Zed asks; `.zed/settings.json` runs `frappe lsp crystalline` and `frappe lsp ameba-ls`. Put this project's matching `frappe` on Zed's login-shell PATH. A one-off `PATH=… zed .` can start the servers initially but may be lost when Zed refreshes the worktree environment.

`frappe make resource` writes a schema, one changeset serving both create and update, seven actions, views, a request spec, and the `create_<plural>` migration that `frappe db diff` would derive for the new table. Resource fields support `string`, `int32`, `int64`, `bool`, `float64`, and RFC 3339 `time`. Append `?` for nullable values (quote these declarations in shells that expand `?`). Append `:server` to a field the server sets, such as `short_code:string:server`: it stays out of the request contracts, the form and the request spec's inputs, and the generated create action gives it a starting value for you to replace (a nullable one stays NULL). Append `:unique` for a unique index and a changeset `unique_constraint`, so a duplicate becomes an error on the field; `short_code:string:server:unique` is a server-set token, and a `:server:unique` number starts random. Required text fields must not be blank. For irregular plurals, use `--plural=people`. Generation refuses existing files and preserves edits around the route and path markers. Review the generated files before running migrations.

Commit `shard.yml`, `shard.lock` and `config/environment.yml`. `shard.lock` pins the Caramel release this application uses, and Frappé runs that release's commands for it; `frappe installations` lists the releases installed on this Mac. Frappé installs dependencies from the lockfile.

Keep `.env`, `lib/`, `.caramel/` and local storage out of version control. Do not deploy local database URLs, secrets or CA material. Production supplies its own `DATABASE_URL`, `MIGRATION_DATABASE_URL`, `APP_SECRET`, `APP_ORIGIN`, and private application socket.
