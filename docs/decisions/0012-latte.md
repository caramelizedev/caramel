# ADR 0012: Latte supervises one PostgreSQL cluster, DNS and an HTTPS proxy per user, leaves applications to the terminal, and observes local sites

Date: 2026-09-27

Status: accepted.

## Context

Latte has to supervise the application and shared services, watch sources, give instant type feedback and clone databases. It must survive terminal sessions, several projects and daemon crashes, and it must never expose one user's database to another. Latte runs only on macOS: its menu app, port relay, installers and toolchain are all macOS-specific.

`latte daemon` would need starting by hand, and would stop when that terminal closes.

`.caramel` names resolve only through a system resolver entry that needs administrator rights, and Latte's local CA is trusted only after the owner runs `latte trust install`. Caddy's undeclared default `local` CA tries to install itself into the system, Java and NSS trust stores for a `.localhost` name; the [incident note](https://github.com/caramelizedev/caramel-notes/blob/main/research/incident-2026-09-27-caddy-local-ca.md) has the details.

Crema's development tools stop at one application. A developer also wants the database's own view of the queries it runs, a site's HTTP traffic as the proxy saw it, and one trace across several local sites and services, from the machine's menu bar. Latte owns the PostgreSQL cluster, the HTTPS proxy and the menu bar app, so it is where those belong.

## Decision

The rules a developer relies on are stated on the website ([site.html](../../website/source/site.html)), chiefly its Local environment and Commands references and the Latte sections of its Crema reference and Observability guide, in the sections cited below by anchor, and in the doc comments under [src/latte](../../src/latte) and [src/frappe](../../src/frappe). This record states what was chosen. The tools Latte runs come from the toolchain of [ADR 0001](0001-toolchain-and-setup.md).

1. **Latte is a per-user supervisor of shared services.** The `latte daemon` starts, adopts after restart and recovers the shared PostgreSQL 18 cluster, CoreDNS and Caddy (`site#c-local-latte`). The daemon owns processes and databases. It carries no agent protocol state: Frappé commands stay one-shot processes. One Latte per user serves the default ports, which the resolver and the relay point at. Another state root, a check's or a second user's, runs on ports of its own and gets no resolver or relay, and a Latte whose port is held refuses to start that service and names the port's owner before it starts anything; the port variables, the redirect and the `port_in_use` refusal are in `site#c-local-latte` and at `Supervisor`.
2. **Applications run under terminal-owned `frappe dev` sessions.** A session registers a development gateway socket with Latte and stops when the terminal does (`DevGateway`, `DevChild`).
3. **Latte adopts or replaces a service process only after identifying it.**
   - It adopts an unrecorded process only when exactly one of the user's processes runs the service's executable with its exact command line, and refuses when several do. Processes that share the executable's name but not the command line, such as another Latte's services or a check fixture's, do not make the choice ambiguous.
   - It replaces a recorded CoreDNS or Caddy that an earlier toolchain started, as after an upgrade: it stops that process only when its owner record, user, start time and exact command line match and its executable is the same tool in a sibling toolchain's `data/installs`, then starts its own. Any other live mismatch is refused, naming both executables (`ManagedChild`).
   - How it adopts a postmaster that another toolchain's build started is in the PostgreSQL major rule of [ADR 0016](0016-versioning-and-releases.md).
4. **Latte starts on demand, and the login item is opt-in.**
   - **On demand.** When no daemon serves the per-user state, every command that needs Latte services runs `latte daemon --detach`: the newest installed release's `latte`, or the one beside the running `frappe` when that release is the newest, as the one-Latte rule of [ADR 0016](0016-versioning-and-releases.md) says (`LatteClient`). The daemon moves into its own session and writes to `logs/latte.log`, which is retained like the service logs (`Daemon.detach`, `Logs`). Frappé never starts a daemon for a `CARAMEL_HOME` someone set. Checks and fixtures run their own daemons there.
   - **`latte stop`.** It asks the daemon to exit through its control socket (`POST /v1/daemon/stop`) and waits for the instance lock to be released. Services keep running and are adopted by the next daemon (`Daemon.stop`).
   - **Login item.** `latte service install` writes a per-user LaunchAgent and loads it into `gui/<uid>`; its path is in `site#c-local-latte`. The agent runs `latte daemon --detach` with `RunAtLoad` and `AbandonProcessGroup`, and no `KeepAlive` (`LoginItem#render`). Installing takes over from a running daemon. `latte service uninstall` unloads the agent and deletes it.
5. **Every service socket is a Unix socket only its owner can reach.**
   - PostgreSQL listens only on a private, owner-only socket directory inside Latte's state (`listen_addresses = ''`) with SCRAM authentication. It does not use the shared `/tmp/.s.PGSQL.5432`.
   - Application sockets live in the site's owner-only run directory under the same runtime root, not at `/tmp/caramel_app.sock`.
   - The runtime root is a directory under the owner's home, named by a digest of the state root, with the home from the passwd database (`StateSecurity.runtime_root`, `StateSecurity.user_home`). Latte refuses a home that would push a socket path past 103 bytes (`Paths::SOCKET_PATH_LIMIT`).
6. **A site takes the suffix `caramel`, `test` or `localhost`.** A `.localhost` site is reachable without administrator rights (`Site::LOCALHOST_SUFFIX`, `site#c-local-sites`). CoreDNS still serves a zone for every suffix.
7. **Latte never installs trust implicitly.** Latte's Caddy configuration declares every CA Caddy can provision, `caramel` and the implicit `local`, with `install_trust: false` (`Proxy`, at `pki_app`). Trusted browser HTTPS for `.caramel` names needs the owner's one-time trust and resolver installation (`site#c-local-setup`). The trust guard of check fixtures is in [ADR 0001](0001-toolchain-and-setup.md).
8. **`frappe dev` rebuilds on kernel events.** `Caramel::Latte::Watcher` registers `EVFILT_VNODE` kqueue filters on every watched directory and file; how it opens them and rescans a changed directory is at `Watcher`. `frappe dev` hashes the tree only after a kernel event, then waits out a debounce before the type check (`DevSession::DEBOUNCE`, `site#c-local-limits`); a newer change stops an obsolete check or build. The watcher drains with a zero-timeout `kevent` every 25 ms and never blocks the scheduler. There is no `inotify` backend, because Latte is macOS-only.
9. **The type check is reported before code generation.** Every uncached source change runs one `crystal build --stats` with the development flags, and its semantic phase is the Tier-1 check: `frappe dev` reports the check when the compiler reports its last semantic stage, before code generation starts (`DevCommand::Stages`). On failure it shows the diagnostics immediately on the site's error page and in the terminal and skips code generation; on success it continues to the native build (`site#c-local-dev`).
10. **A database branch is a guarded APFS clone.** `frappe db branch create NAME | list | delete NAME` asks the daemon, which applies this guard: `ALLOW_CONNECTIONS false`, terminate other backends, `CREATE DATABASE … TEMPLATE … STRATEGY FILE_COPY`, and always re-allow (`Postgres#guard_connections`). Latte's `postgresql.conf` sets `file_copy_method = clone`, so the file copy is an APFS copy-on-write clone. `create` prints the branch URL (`site#c-local-databases`), and `frappe dev --branch NAME` runs the app against it (`site#c-local-dev`).
11. **A crash never leaves a database closed.** The daemon restores `ALLOW_CONNECTIONS` on every Caramel database, both in its SIGINT/SIGTERM exit path and at every start. Starting after a SIGKILL therefore repairs a guard that a crash left in place (`Postgres#release_guards`).
12. **The managed cluster collects statement statistics.** Latte preloads `pg_stat_statements` and `auto_explain`; what each records, and the threshold, is in `site#c-cremaref-latte`. `auto_explain` writes its plans as text (`auto_explain.log_format = text`). A cluster that lacks the preload or a setting restarts once through the ordinary start path.
13. **Statistics live in a schema of their own, in development databases only.** The schema is `caramel_stats` in each site's development database; the spec database has none. The extension is created there, the development migration and runtime roles may use the schema, and no role is granted `pg_read_all_stats`, so a role reads the statement text of its own statements only. `frappe db dump` excludes the schema and the extension. `frappe db diagnose` reads the statistics when the extension is present.
14. **Control API version 2 carries each site's errors.** Latte serves `/v1/…` and `/v2/…` through the same routes, and every body names the version asked for (`ControlAPI`). A version 2 site adds `errors`, the number of errors its development application reported since `frappe dev` started, and `last_error`: `{fingerprint, error_class, location, at}` or null, with a location of at most 200 characters and never a message. The development gateway reports both on its status endpoint; a gateway that predates them reads as zero errors. A version 1 site is unchanged. Frappé, Corretto and Latte.app ask for version 2; a Latte that serves only version 1 is refused with `latte stop` as the remedy. How versions are served and refused is in [ADR 0016](0016-versioning-and-releases.md).
15. **Latte.app raises alerts.** A site's menu title shows its error count, its submenu the newest error, and an Open inspector item opens `/__caramel/dev/inspector`, which needs a signed-in browser (`site#c-crema-menu`). A build that turns to `build-error`, or an error fingerprint not yet seen for that site in this run, adds to a count beside the status item and, when macOS allows, posts a notification that opens the inspector. The first snapshot after launch seeds what is known and alerts nothing; opening the menu clears the count.
16. **Each site has its own Caddy access log.** Latte's proxy configuration holds one logger per registered site, `site_<id>`, that writes JSON to `<logs>/sites/<id>/access.log`; its mode, size and retention are in `site#c-cremaref-latte`. The HTTPS server maps each domain to its logger and skips unmapped hosts, and the default logger excludes `http.log.access`, so `proxy.log` carries no access lines. The directory is the one Frappé keeps `app.log`, `compiler.log` and `events.jsonl` in (`Paths#site_log_dir`). `frappe logs access` prints the file, and Caddy redacts `Cookie` and `Authorization` (`site#c-crema-access`).
17. **Latte collects local traces over OTLP/HTTP on loopback.** The daemon listens on `127.0.0.1:4318`, the OTLP/HTTP port, for `POST /v1/traces` with a JSON body. The body, trace, span and byte limits, and the `Host` it answers 421 to, are in `site#c-cremaref-latte`; against the byte limit each span is charged its strings plus 128 bytes (`Collector::SPAN_OVERHEAD`), and the oldest traces go first (`Collector#evict`). It refuses protobuf with 415. A busy port leaves the collector `unavailable` and the daemon running. `CARAMEL_LATTE_OTLP_PORT` moves the collector's port; the latte-daemon check uses that to pick a free port (`Collector.port`). The collector serves no reads: control API 2 lists traces (`GET /v2/traces?limit=N`), returns one (`GET /v2/traces/<id>`) and reports the collector in `/v2/status`, and version 1 has none of it. `frappe dev` forwards each trace of the application to the collector as OTLP JSON under the project's name (`DevEvents#forward`), and the inspector and `frappe trace --md` add an "Across services" section when another service joined the trace (`site#c-crema-collector`). The collector stays out of the three-service readiness states.

## Reasons

- A shared supervisor with terminal-owned apps keeps many projects running without Docker, while each project's lifecycle stays under its developer's control.
- Starting the service supervisor on demand removes a manual step without adding an agent daemon. Frappé commands stay one-shot and stateless, and the daemon still carries no agent protocol state. The login item is opt-in because it changes what runs at login.
- launchd kills a job's whole process group when the job exits. Without `AbandonProcessGroup`, a crash or `latte stop` would take PostgreSQL, CoreDNS and Caddy with it.
- Rejected: `KeepAlive` on the login item, because a daemon that exits since another one is already running would restart in a loop, and on-demand start already recovers from a crash.
- A private socket keeps "no TCP" and "no Docker" without giving other local users a path to the cluster. `/tmp` is shared by every user on the machine, so neither PostgreSQL's nor an application's socket lives there.
- The runtime root is short enough for macOS's 104-byte socket paths, and under the owner's home, where another user cannot create the directory first, as they could in `/private/tmp`.
- RFC 6761, the IETF special-use names standard, reserves `.localhost` for loopback. Chrome resolves its names to loopback itself, without any system configuration. CoreDNS serves a zone for every suffix because Latte's readiness probe queries each registered name.
- Trust stores belong to the machine owner, so Latte adds trust only when the owner asks.
- Kernel events remove the full-tree polling cost.
- A multi-file save that outlasts a shorter debounce window only cancels a check and costs CPU, since a newer change stops an obsolete check or build.
- Crystal 1.21's event loop cannot wait on a kqueue descriptor, so the watcher polls it without blocking.
- A type check before code generation gives the fastest feedback Crystal allows today.
- One CLI (`frappe`) for every developer command avoids a second binary vocabulary.
- `pg_stat_statements` answers "which statement is slow" with the cost the database measured, and `auto_explain` writes the text and plan of a statement of 250 ms or more to `postgres.log`; application statements carry placeholders, so no bind values reach it. Utility statements are not tracked, because `ALTER ROLE … PASSWORD` carries a literal, and a role sees only its own statements' text.
- Keeping the statistics views out of `public` keeps them out of SugarORM's introspection and Corretto's catalog fingerprint.
- `frappe db dump` leaves the schema and the extension out because `restore` runs as the migration role, which cannot create an extension.
- The statement tags Crema adds ([ADR 0027](0027-crema.md)) make those statistics attributable.
- Local OTLP SDKs speak HTTP over TCP, so the collector is an exception to the Unix-socket rule. Any local process may write, as with any OpenTelemetry collector, but a browser page cannot through DNS rebinding, because its `Host` is not the collector's, and no writer can grow the daemon past the byte ceiling; only the owner can read, over the control socket. Traces hold span names and attributes the exporter chose, never a Caramel secret ([ADR 0027](0027-crema.md)).
