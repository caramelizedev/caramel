# ADR 0010: Corretto runs every example in a rolled-back savepoint on a Latte worker database, with in-process requests, wire-level fakes and parsed HTML expectations

Date: 2026-09-27

Status: accepted.

## Context

Corretto needs subcutaneous sessions with `sign_in`, custom matchers, a ban on mocks, per-worker branches, per-example savepoints, catalog resets, synchronous queue drains, wire-level fakes through a local proxy and `--concurrency`. Two constraints shape it: Crystal's shared compiler cache makes parallel `crystal spec` processes overwrite each other's output, and a least-privileged runtime role cannot run DDL.

Raw HTML substring assertions couple behavioral specs to quote style, attribute order and escaping spelling. They also let unrelated elements satisfy a check. Blueprint gives views a readable Crystal vocabulary, but rendering an expected view through the same code would hide renderer defects.

## Decision

The rules a spec relies on are stated on the website ([site.html](../../website/source/site.html)), chiefly its Corretto reference and its HTML testing guide, in the sections cited below by anchor, and in the doc comments under [src/caramel/corretto](../../src/caramel/corretto) and in [src/frappe/corretto_runner.cr](../../src/frappe/corretto_runner.cr). This record states what was chosen.

1. **`frappe corretto` runs each worker as its own compiled spec binary on its own clone of the migrated spec database.** This is Tier 1 of the isolation. `frappe corretto [SPEC_PATHS…] [--concurrency=1..8]` migrates the spec database once and asks Latte (`POST|DELETE /v1/sites/:id/test-workers/:n`) to clone one worker database per worker from it, behind the connection guard. It splits the spec files round-robin, runs each worker as its own compiled spec binary, prefixes and aggregates the workers' output and exit statuses, then drops the workers. `frappe test` does not exist; `frappe corretto` is the command. The preparation phases it prints with their durations, the forwarding of an unfinished output line after five quiet seconds and the total duration are in `site#c-corretto-run` and `CorrettoRunner::QUIET`; the syntax is in `site#c-commands-frappe`.
2. **Runs in one project serialize on a whole-run lock.** The lock is `.caramel/corretto/run.lock`, taken after the mock scan. Every run uses workers w1..wN, the same binaries and the same Latte databases, so a second run prints `Corretto: waiting for another run in this project` and starts when the first releases the lock (`CorrettoRunner::RunLock`, `site#c-corretto-run`).
3. **A worker's spec binary is kept and runs again while nothing it was built from changed.** It stays in `.caramel/corretto/`, so a rerun with no change compiles nothing; the inputs that must be unchanged are listed on `CorrettoRunner#start_builds`. Spec binaries build in the development build's environment; a worker's settings, its database and the `.env.test` values, apply when its binary runs, not when it compiles. They build while the application builds and migrates the template and Latte clones the workers, once the mock scan and the spec database checks have passed.
4. **Every example runs in a transaction and a savepoint that are rolled back.** This is Tier 2. A global `Spec.around_each` opens a transaction and SAVEPOINT on the worker's single connection and binds it with `SugarORM::Repo.bind`. The example, including its in-process requests, runs on that connection, and the savepoint is rolled back afterwards (`Corretto::Worker`, `site#c-corretto-run`).
5. **A catalog fingerprint finds DDL that escaped the transaction, and the worker database is reset.** This is Tier 3. At boot Corretto records a catalog fingerprint: a hash of `pg_class`, `pg_attribute`, `pg_index` and `pg_constraint` rows in the public schema. If an example leaves the catalog changed, Corretto resets the worker database from the migrated template through Latte and reports which example did it. Examples tagged `catalog` run without the savepoint, on a migration-role connection, and always reset afterwards (`Corretto::Worker`).
6. **Latte sizes the spec roles for parallel and catalog examples.** The spec migration role's connection limit is 8 and the runtime role's is 24. The runtime limit also covers Cold Brew's pool and listener.
7. **A spec worker starts from a cleared environment, and the application's test settings come from `.env.test`.** A worker never receives the development `.env`; of the shell's environment it receives `CORRETTO_SEED` alone. Settings the application reads itself come from the committed `.env.test`, in the `.env` format, which Corretto merges under its own keys. It refuses keys it or the toolchain supplies; the keys and prefixes are in `site#c-corretto-setup` and `CorrettoRunner::RESERVED_TEST_KEYS`.
8. **A session is a signed cookie the browser holds, and a spec signs in by writing it.** `Caramel::Session` is an HMAC-SHA256 signed `__Host-caramel_session` cookie that carries its issue time and is verified in constant time. Nothing is held server-side. Its keys are derived from the application secret and from each secret in `APP_SECRET_PREVIOUS`: the current secret signs, every one verifies. The cookie's attributes, its size limit, its absolute window (`session_max_age`), the clock skew it accepts, what a copied cookie reads after `sign_out`, and how actions read, write and clear `session` are in `site#c-security-sessions`, `site#c-actions-request` and `Caramel::Session`. `client.sign_in(user)` writes `user_id` into the client's session cookie (`site#c-corretto-browser`).
9. **Requests run in-process on the example's connection.** `Corretto.session { |client, db| … }` yields a client that drives `Caramel::Application#handle` directly, and the example's database connection. The client keeps a cookie jar, attaches CSRF, `Origin` and `Host` automatically, and follows redirects. The body forms a request takes are in `site#c-corretto-client` and `Corretto::Client`, the browser behaviour in `site#c-corretto-browser`. `Corretto.tmpdir` is a private directory for the files an example writes, removed when the example ends.
10. **Matchers assert against observable egress and state.** They are `have_status`, `render_partial`, `redirect_to`, `have_header`, `render_page`, `have_html` and `have_row`; `have_row` is a macro, so unknown fields fail compilation (`site#c-corretto-matchers`, `Corretto::Matchers`).
11. **HTML expectations are Blueprint-shaped requirements matched against parsed elements.** `have_html(within: nil, count: nil, strict: false) { … }` and a block overload of `render_partial(target, swap:)` each accept one root requirement. They reuse Blueprint 1.1.0's standard element declarations with Corretto registration macros, recording text and attributes without rendering them (`Corretto::HTML::PatternBuilder`). Default patterns select requirements and strict mode compares the complete subtree. The website's HTML testing guide states the complete matching contract: `site#c-testing-requirements` (defaults, text, classes, attributes, leaf values, `plain`, custom elements), `site#c-testing-strict` (strict mode, partial envelopes, what raises even under negation) and `site#c-testing-refusals` (what fails compilation). Beyond the guide: a string checks descendant text; direct text coalesces across comments in both modes; counts apply to complete matching roots; negation inverts the full result. Response matchers parse too: a full page needs a doctype in its actual source and a parsed title, and title matching keeps substring semantics. Failure diagnostics keep paths, observed values and counts and bounded excerpts after releasing the document. The [case inventory](https://github.com/caramelizedev/caramel-notes/blob/main/research/corretto-html-testing.md) lists the cases.
12. **Lexbor parses the HTML, pinned as a development dependency and required only through Corretto.** The parser is [Lexbor 3.6.4](https://github.com/kostya/lexbor/tree/v3.6.4), pinned in the framework and in generated applications. Its HTML5 parser decodes attributes and text, and handles document and fragment parsing. An internal adapter owns native documents, chooses table and select fragment contexts, validates selectors and frees memory after each assertion (`Corretto::HTML::Document`). There is no global DOM cache. What installing it needs, what production installs omit and the lockfile pin are in `site#c-testing-install`. The native build runs once per toolchain: Frappé runs each dependency's postinstall script itself, after `shards install --skip-postinstall`, and keeps the files the script writes into its directory in the toolchain's `postinstall-cache`, keyed by the dependency's name and version, so the next application copies them (`Caramel::Frappe::Postinstall`).
13. **An `hx-partial` envelope is parsed as htmx reads it.** Before DOM parsing, token metadata renames actual `hx-partial` envelopes to templates, matching htmx's treatment of table and select payloads. The adapter moves their parsed content into restored envelope nodes without adding wrappers. Ordinary template content stays inert, and raw text and comments are never envelopes (`PartialSource`). Lexbor's shard does not expose native template content, so a private binding follows the pinned C layout (`TemplateNative`); review it when upgrading that dependency.
14. **Behavioral specs assert decoded elements; byte tests and browser checks keep what only they prove.** Behavioral specs and generated examples use decoded element assertions. Exact byte tests remain for serialization and escaping, and browser checks for actual htmx morphing. Expected nodes are independent data, never view invocations or rerendered expected HTML; escaping mutations must fail.
15. **The linter allows `p` and nested braces only inside expectation blocks.** Caramel's Ameba runner recognizes them there and keeps the debug lint elsewhere (`site#c-testing-prove`, `HTMLExpectationVisitor`). The line limit is the same inside an expectation as outside.
16. **One framework client makes outbound HTTP calls, and it refuses the host's own network.** `Caramel::Outbound` connects directly in production; when `Outbound.proxy` is set, it sends absolute-form HTTP/1.1 requests to that proxy. A direct call resolves the host first, refuses with `Outbound::Blocked` an address on the host's own network, and connects to the vetted address itself. The refused address classes, `Outbound.allow_private`, the proxy's exemption from the check, the response size cap and the deadline are in `Caramel::Outbound` and `site#c-security-redirects`.
17. **Third parties are faked at the wire.** Corretto starts a local TCP proxy for the suite. `Corretto.stub_wire(url, method:).to_return(…)` matches real request bytes by method and absolute URL, an unmatched request gets a 502, `Corretto.wire_requests` records traffic, and stubs reset after each example (`site#c-corretto-wire`, `Corretto::Wire`).
18. **Mocks do not compile and do not run.** Loading a mocking library is a compile error. `frappe corretto` also scans spec files for mocking APIs and refuses to run, naming the file and line; the calls it looks for are in `site#c-corretto-mocks`.
19. **Specs drain queues synchronously.** Specs call `Caramel::ColdBrew.drain_queue!(db, "default")`, under the drain rule of [ADR 0009](0009-cold-brew.md). No worker fibers run under `CARAMEL_ENV=test` (`site#c-corretto-jobs`).
20. **A full run checks the requirements.** When every worker passes a run with no spec paths, `frappe corretto` asks the application for its requirement ids (`requirements --ids`) and fails unless an example that ran names each, as a token, in its full description: `AC-1` is not named by `AC-12` (`CorrettoRunner.uncovered`). The failure names each id no example names. The full description is the groups' descriptions and the example's own, joined by spaces. Each worker writes the descriptions it ran to `.caramel/corretto/w<N>.examples` (`CORRETTO_EXAMPLES`). A run of chosen paths checks nothing, and an application that declares no requirements is not checked. What declares an id is in [ADR 0035](sweettalk/0035-reads-and-rules.md).
21. **Property cases run a calculation on generated arguments.** `Corretto.property(Billing.share)` runs a calculation, declared as [ADR 0035](sweettalk/0035-reads-and-rules.md) says, on 200 cases, in the example, outside a session and with no database. Each argument is drawn from what its type declares. What each type draws, what a refused case, a failing case and a run of only refused cases do, the seed and `CORRETTO_SEED`, what the run returns and what does not compile are in `site#c-corretto-properties`, `Corretto.property` and `Corretto::Property`.

## Reasons

- Running requests in-process on the example's own transaction lets one rollback undo the example's writes, its requests' writes and its jobs' writes. No global cleanup code is needed.
- The rollback does not undo filesystem writes, so `Corretto.tmpdir` gives an example a directory Corretto removes.
- A catalog fingerprint detects exactly the un-rollbackable case, so resets happen only when needed. A changed catalog means DDL escaped the transaction. `catalog` examples run on a migration-role connection so that they may run DDL.
- Separate compiled spec binaries are the only reliable way to run workers in parallel with Crystal 1.21: they avoid the compiler-cache clash.
- Spec binaries need no database, so they build while the template migrates and the workers are cloned.
- An unfinished output line is forwarded after five quiet seconds so progress dots show in time.
- Every run uses workers w1..wN, the same binaries and the same Latte databases, so two runs in one project cannot overlap. Rejected: pid-derived worker names, which would break the 1..8 worker contract and Latte's role limit.
- Parallel and catalog examples need more connections than one worker holds, so Latte raises the spec roles' limits.
- Deriving keys from the current secret and from each previous one lets a secret rotate without ending every session and open form at once. Because nothing is held server-side, a copied cookie reads until its window ends, after `sign_out` too; an application that must end a session everywhere keeps a revocable row.
- Connecting to the vetted address means a user-supplied URL cannot reach the host's own network and a DNS answer cannot change between the check and the connection. A proxy skips the check because the proxy resolves the host.
- A proxy the framework client already knows about intercepts real HTTP bytes without monkey-patching any Crystal method. An unmatched request gets a 502, so no test reaches the real network.
- No tautological mocks: specs test subcutaneous behaviour against real PostgreSQL branches and real morphed HTML, and read as ingress, state and egress.
- Decoded elements make specs independent of quote style, attribute order and escaping spelling.
- Blueprint's finite vocabulary catches misspellings at compile time; runtime failures name the expectation path and observed content.
- Requirements read like the project's views, with one familiar vocabulary.
- Invalid expectations, selectors and missing scopes raise, because otherwise they would make negative assertions pass.
- Rejected: rendering a second Blueprint tree, because shared escaping defects would pass.
- Rejected: raw text helpers, because they cannot establish ancestry.
- Rejected: a homegrown HTML parser, because it repeats mature HTML5 parsing machinery.
- Rejected: browser-only assertions, because they add process overhead to request specs; browser tests stay for interactions.
- Rejected: CSS as a second complete public DSL; it serves only `within:`.
- Precedent: Rails scopes nested requirements to a matched ancestor and separates partial requirements from equality. Laravel shows that text presence alone does not prove structure. Phlex shows that a view DSL need not be the assertion engine and that a real parser should be used. These are design precedents, not execution models: Corretto drives in-process requests against real database branches.
