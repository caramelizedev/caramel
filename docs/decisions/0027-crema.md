# ADR 0027: Crema traces every request, job and schedule run, keeps secrets out of everything it writes, and gives production access through an owner-only socket

Date: 2026-10-03

Status: accepted.

## Context

A request that fails or slows down must be traceable from the log line to its queries, its background jobs and the outbound calls it made, in development and in production. Frameworks that solved this (Rails, Phoenix, Laravel) put one event at the centre and let sinks decide what to keep. Caramel needs the same without a second runtime, without secrets in logs and without a diagnostic that costs a production binary anything.

A production incident needs the running process's own view: what is in flight, which errors repeat, which statements are slow, and what one person's request did. The answer must not widen the public attack surface, must not put exception messages or request paths in a log or a table, and must cost an application that does not want it nothing.

## Decision

The rules an application relies on are stated on the website ([site.html](../../website/source/site.html)), chiefly its Crema reference and its Observability guide, in the sections cited below by anchor, and in the doc comments of [src/caramel/crema.cr](../../src/caramel/crema.cr) and under [src/caramel/crema](../../src/caramel/crema). This record states what was chosen.

1. **Crema's core compiles into every application, and every other part is an opt-in require.** Crema is `Caramel::Crema`. The core, `src/caramel/crema.cr`, requires no database or Cold Brew code. Opt-in parts live under `caramel/crema/…` and register through `Crema.on_start`, `Crema.command` and `Crema.console_page`; they redefine no method. What runs always, by opt-in and in development only is in `site#c-cremaref-where`.
2. **One trace per unit of work.** `Crema.request` traces each routed request, `Crema.job` each claimed job and `Crema.schedule` each schedule run. A trace has a request id, a trace id and a span id (`Ids`), binds to its fiber and to `Log.context` (`Crema.bound`), and goes to every sink when it finishes (`Trace`). Static files and the 400 and 421 refusals are not traced. The request id comes from a well-formed inbound `X-Request-ID` and is returned as `X-Request-ID`; a valid W3C `traceparent` supplies the trace id and `parent_id`, and its sampled bit is kept as `parent_sampled`. `Crema.trust_trace_context = false` ignores both inbound headers; the environment variable that sets it is in `site#c-cremaref-api`. The accepted forms are in `site#c-cremaref-ids`.
3. **A trace is named by its route template, never by a path.** The matched route's template, such as `/books/:id` or `/:tenant/books`, names the trace (`GET /books/:id`); an unmatched request is `GET (none)` (`Crema.routed`, `site#c-cremaref-log`).
4. **One wire format, version 1.** `TraceEvent`, `SpanEvent`, `RepeatEvent`, `ErrorEvent` and `BuildEvent` in `crema/event.cr` are the one definition the application, Frappé, the ops socket and Latte share (`WIRE_VERSION`). Production detail omits request paths, bind values, SQL source lines, messages and backtraces (`Detail`). `ErrorEvent.location`, a project-relative `file:line:column` of the fingerprint frame, stays in production.
5. **One canonical log line per finished trace and one per error report.** The `crema` log source writes them; `CARAMEL_LOG_FORMAT` chooses JSON or text and `LOG_LEVEL` the level. The messages, fields, defaults and the `data_` prefix of a JSON key that collides with a reserved one are in `site#c-cremaref-log` and `site#c-cremaref-env`.
6. **Errors go through `Crema.report`.** It builds an `ErrorReport`: class, redacted message and backtrace, a fingerprint, `handled`, source and ids. The fingerprint covers the class and the first application frame's file and method, never a line, column or message (`ErrorReport.fingerprint_of`). `Crema.report` never raises; a sink that raises is logged. `Crema.on_error` hooks receive reports, and a fiber reports an exception once. The fields are in `site#c-cremaref-errors`.
7. **The secrets rule.** Logs, tail events, metrics labels and every table Crema writes never carry exception messages, SQL bind values, request paths or bodies. Redacted messages and backtraces exist only in the in-memory error ring and in development-only surfaces. `Crema::Redact` scrubs every message and backtrace frame first; what it removes is in `Redact` and `site#c-cremaref-errors`.
8. **Sinks decide what to keep.** A `Sink` says whether it wants spans (`records?`, asked once per trace) and receives `finished` and `reported` on the reporting fiber without blocking. The log, metric and tail sinks are built in (`LogSink`, `MetricSink`, `TailSink`); `Crema.subscribe` adds one. The thresholds `Crema.slow_request`, `Crema.slow_job` and `Crema.slow_query` flag slow work (`site#c-cremaref-api`).
9. **`serve` and `work` start one runtime.** They call `Crema.start` with the role, database pools, Cold Brew service and application. It runs the `Crema.on_start` blocks, and `Runtime#stop` runs the stoppers those blocks returned, newest first (`Runtime`).
10. **SugarORM stays independent.** `SugarORM::Repo` yields each statement through two hooks, `observe` and `observe_checkout`, that only yield. `caramel/crema/sql` redefines them: it times the statement as an `sql` span, counts slow statements and, when the trace records, repeated ones (`Sql`, `site#c-cremaref-log`). The span's name is the verb and first table (`Crema.summary`); its detail is the parameterized SQL, never a bind value.
11. **Statements name their code.** Inside a trace every statement starts with a comment that names the action, job or schedule, and every pool carries an `application_name` (`Crema.sql_tag`, `site#c-cremaref-sql`). The tag is prepended and holds nothing that varies per request.
12. **Work carries its trace.** `caramel_jobs.context` (jsonb, a framework migration of [ADR 0009](0009-cold-brew.md)) holds the enqueuing trace's `traceparent`, request id and, for a debug trace, `"debug":true`. The job's trace continues that trace; its `parent_id` is the enqueuing span. A schedule run starts a trace of its own. `Caramel::Outbound` times each call as an `http` span and sends `traceparent` unless the caller set one; cache reads count hits and misses; views are `view` spans and only the outermost counts in `view_ms` (`site#c-cremaref-ids`, `site#c-cremaref-log`). `Crema.measure` with the `domain` kind times a named domain operation, such as `Ordering::Order#place`, with no detail and no counter; an exception sets the span's `error_class` (SweetTalk's use is in [ADR 0046](sweettalk/0046-transactions.md)). The inspector indents spans inside a `view` or `domain` span.
13. **Cold Brew reports through Crema.** A job's failure, a failing hook and the worker, maintenance and scheduler loops call `Crema.report`. The sources they report under are in `site#c-cremaref-log`.
14. **Development surfaces are compiled out of production.** They need `-D caramel_development` and `CARAMEL_ENV=development`: the rich error page, the event sink, `Server-Timing`, the `dump` span, and a query's binds, their PostgreSQL literals and source line. Elsewhere `dump value` returns the value untouched. A `nil` bind is recorded as a lone NUL character and shown as `NULL` (`NULL_BIND`). What the error page shows, the `CARAMEL_EDITOR` presets and template, and `dump` are in `site#c-cremaref-dev` and `site#c-crema-errors-dev`.
15. **`frappe dev` keeps the events.** It listens on a private socket (`CARAMEL_DEV_EVENTS`); the application's dev sink writes each finished trace and unattached error there as a JSON line (`DevSink`). Frappé keeps the newest in memory and appends every line to the site log's `events.jsonl`, which `frappe traces`, `frappe trace REF [--md]` and `frappe errors` read without a session. `frappe trace REF` also resolves the fingerprint of an error that happened outside a trace, and prints that error and its backtrace. `frappe errors` prints the MRDP diagnostics `RUNTIME` and `REPEATED_QUERY` and leaves out what happened before the newest successful build. Counts, REF forms and exit codes are in `site#c-cremaref-frappe`.
16. **The inspector is served by the development gateway to a signed-in browser only.** It is at `/__caramel/dev/inspector` on the development origin: requests, traces with a waterfall, errors by fingerprint and builds. The development session is the `__Host-caramel_dev` cookie, which the gateway sets only on a single-use link, `/__caramel/dev/sign-in?nonce=…` (a 256-bit nonce), that `frappe dev` prints and opens and `frappe open` mints through the owner token. The inspector pages answer 403 without the cookie; `/__caramel/dev/trace.md?id=` needs the cookie and the `X-Caramel-Dev` header; `status` shows an unsigned client only the generation and state. A query's display layout is display only: a copy writes the statement as it ran (`SqlFormat`); each bind is listed beside its `$n` (`Render.query_card`). The toolbar, the inspector and the ops console follow the system's light or dark appearance, and a Theme button overrides it. The inspector and the console share one palette file; the toolbar keeps its own. Compile errors link to the editor, and Latte.app opens the inspector. The toolbar, the pages, the copy buttons and the sign-in limits are in `site#c-cremaref-dev`, `site#c-crema-inspector` and `site#c-local-dev`.
17. **The ops socket is the only door into a running process.** `serve` binds an owner-only Unix socket inside the running binary; `work` binds one only when `CARAMEL_OPS_SOCKET` names a path, and `off` disables it. A socket whose directory is not private is not bound, and the application keeps serving. The ops socket always needs a private directory, also when the application socket's directory admits a group ([ADR 0032](0032-production.md)); `CARAMEL_OPS_SOCKET` places it in one. At start the process writes a random 256-bit key to `<socket path>.key`, and every request must present it (`Ops`, `OpsKey`). Modes, the default path, what happens to a live or a dead socket file and the key file's life are in `site#c-cremaref-ops` and `site#c-cremaref-env`.
18. **Every ops request passes three guards, in the order 421, 401, 403.** A request whose `Host`, with or without a port, is not one of the four local names answers 421. A request without the key answers 401 `unauthorized`; the key is a bearer token on any request, or the `caramel_ops` cookie on GET only. A write with an `Origin` header answers 403. JSON errors read `{"version":1,"error":{"code","message"}}`. The names and the other answers are in `site#c-cremaref-ops`.
19. **The API is version 1 and serves two in-memory rings.** The endpoints are under `/v1/` (`site#c-cremaref-ops`). The error ring keeps the newest report of each fingerprint with its count; the trace ring keeps the newest traces that failed, ran slow or carried a debug token, with their spans (`ErrorRing`, `TraceRing`). Both are bounded (`site#c-cremaref-limits`), start empty and are lost on restart. `/v1/errors/<fingerprint>` is the only answer that carries an exception's redacted message and backtrace.
20. **Metrics are Prometheus text with bounded labels.** `/v1/metrics` serves the `caramel_*` families listed in `site#c-cremaref-metrics`. Labels are route templates, class names and statuses; an unmatched route is `(none)` (`Prometheus`).
21. **A debug token traces one person's requests for a bounded time.** It is `"<expires>.<hmac>"`, signed with a key derived from the application's secret. Sent as `X-Caramel-Debug` or the `__Host-caramel_debug` cookie, it makes a request a debug trace: recorded, answered with `X-Caramel-Trace`, kept in the trace ring and passed to the jobs it enqueues. Lifetimes are in `site#c-cremaref-debug` and `site#c-cremaref-limits` (`DebugToken`).
22. **The console is read-only HTML on the same socket.** It is reached with `ssh -L`; `ops console` prints a URL with `?key=`, which `GET /` swaps for the cookie and a 303. Its pages load only their own stylesheet and script under a strict content security policy (`Console`, `site#c-crema-console`, `site#c-cremaref-ops`).
23. **Production access is a fixed set of binary commands.** `APP ops …` is the socket's client and reads the key file; `APP jobs …` and `APP db diagnose` (which `frappe db diagnose` runs) need the database and no running application. `jobs show` is the one place a job's stored error is read, and it prints to the operator's terminal only (`Jobs::SHOW`). `usage` lists registered commands. Syntax is in `site#c-commands-app`; behaviour and exit codes are in `site#c-cremaref-commands`.
24. **The recorder is opt-in and stores aggregates only.** `require "caramel/crema/recorder"` keeps per-minute aggregates in `caramel_metrics`; new applications require it in `config/application.cr`. The table belongs to Cold Brew's framework migrations ([ADR 0009](0009-cold-brew.md)), so every application has it and only one that requires the recorder writes it. A row never holds a bind value, path, message, backtrace or trace. A write that fails logs a warning, discards that batch, counts it in `dropped["recorder"]` and changes nothing for the work it measured. `APP insights` and the console's Insights page read the rows and compute percentiles from the summed histograms (`Insights`). Columns, kinds, keys, the flush interval, retention and the key limit are in `site#c-cremaref-recorder` (`Recorder`).
25. **The OTLP exporter is opt-in and sends nothing until an endpoint is set.** `require "caramel/crema/otlp"` exports traces as OTLP/HTTP JSON when `OTEL_EXPORTER_OTLP_ENDPOINT` or `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` is set. Sampling is decided once per trace (`Otlp::Sampler`); a debug trace is always sampled, and an unsampled trace that ends in error exports its root span only. The variables, samplers and warnings are in `site#c-cremaref-otlp`.
26. **Exported spans name the route and the SQL, never a path, bind value or message.** A request is a server span, a job a consumer span and a schedule an internal span; each SQL statement and outbound call is a client child. Attributes follow OpenTelemetry's HTTP, messaging and database conventions. `db.query.text` is normalised and cut first (`OtlpJson.sql_text`). An error adds status error and an `exception` event with `exception.type` only.
27. **An exporter failure never reaches the work.** A bounded queue feeds one fiber that posts in batches with a plain `HTTP::Client`. A refused or failed post drops the batch, counts it in `dropped["otlp"]` and logs at most once a minute (`Otlp::Exporter`; sizes in `site#c-cremaref-otlp`).

## Reasons

- One event with pluggable sinks keeps logs, metrics, the inspector and exports in agreement, as Rails' event reporter and Phoenix's telemetry do.
- A fingerprint without lines or messages keeps one defect in one group across deploys and keeps secrets out of grouping keys.
- Reusing the existing redaction and application-frame rules gives one classifier.
- With `trust_trace_context` off every request gets fresh ids and no parent, so a client can neither choose its trace nor force sampling.
- A statement tag makes `pg_stat_activity` and PostgreSQL's logs name the code that ran the statement. It is prepended, so a trailing comment or `;` cannot swallow it, and it holds nothing that varies per request, so prepared statements stay reusable. The pools' `application_name` makes every backend attributable.
- A `domain` span names the operation a trace ran, which its SQL alone does not; it carries no arguments or ids, so production detail keeps it whole.
- The toolbar keeps its own palette because it lives in a shadow root and never changes the page's `<html>`.
- Rejected: logging exception messages. Dependency errors carry URLs and form values.
- Rejected: storing errors, error messages, backtraces or traces in PostgreSQL. The database keeps aggregates only.
- A Unix socket in the binary reaches the live fibers, pools and rings, which no sidecar can, and adds nothing to the public listener; Phoenix's remote shell and Go's pprof taught the same lesson, and the Host and Origin guards follow Tidewave's. The Host guard stops DNS rebinding.
- The key file is the boundary. A TCP forward discards socket permissions, but the key file cannot be read from the operator's laptop.
- A fixed command set replaces evaluating code, which Crystal cannot do at runtime.
- Bounded, expiring probes follow `recon_trace`: every token has a time limit and every ring a size.
- `db.query.text` is normalised before export so that a literal written into a statement is not exported.
- OTLP headers bound for an `http://` endpoint off the loopback interface are warned about because they travel in clear.
- The exporter posts with a plain `HTTP::Client` so that it does not trace itself.
- Rejected: a Unix-socket forward, because a browser cannot open one and a relay is a TCP port again.
- Rejected: a token for browsers only, because any local process can send the CLI's headers.
- Rejected: a web console on the public listener.
- Rejected: an MCP daemon. Agents get stateless command-line tools, not daemons.
- Deferred: CPU profiling and `-Dtracing` builds.
- Research: [observability](https://github.com/caramelizedev/caramel-notes/blob/main/research/observability.md).
