# ADR 0036: SweetTalk compiles the context map, and every relationship between contexts is declared, checked and used

Date: 2026-10-08

Status: accepted.

## Context

An application with a rich domain has no word for a bounded context, and nothing stops one context from reaching into another's types. Naming the relationships is not enough. A reader cannot tell which context is the core of the business. An upstream context cannot say which of its names others may depend on, so every follower depends on all of it. An application that talks to a payment gateway or a carrier has no place in its domain for that translation. A call such as `Catalogue.price_of(tea)` is a dependency as much as a type name, and a map that reads only type names misses it.

Following is one-way. The followed context owns the model, any context may follow it, and nothing records who must agree to a change. Two contexts that own part of a model together, such as a voucher Pricing gives and Billing spends, either put it in one of them, so the other follows a model it has no say in, or keep two copies that drift. A model shared this way also grows: a word one context needed lands beside the shared ones.

A map that refuses only a name with no edge drifts the other way. An application that moved the work across five contexts into its own code kept five `follows:` edges nothing named, and each still counted in the cycle check.

## Decision

The rules an application relies on are stated on the website ([site.html](../../../website/source/site.html)), chiefly its Domain-Driven Design guide, in the sections cited below by anchor, and in the doc comments under [src/caramel/sweet_talk](../../../src/caramel/sweet_talk) and [src/frappe](../../../src/frappe). This record states what was chosen.

1. **A context adopts another with `follows:` or translates it in a `border`.** `follows: Other` on a context lets it use `Other`'s types as they are. `border Other do … end` holds the context's only code that may name `Other::` without following it. A context has one border per other context or outside system, as the rule for contexts across files in [ADR 0030](0030-scope-and-modules.md) says (`site#c-sweettalk-contexts`, `site#c-sweettalk-files`).
2. **The context map is checked at compile time.** `follows:` and the code of a border draw dependency edges, and a `whenever` for another context's event draws an event edge. Only dependency edges count in the cycle check, so two contexts may react to each other's events. An edge to an unknown context, a foreign name outside a border and a cycle of dependency edges do not compile. The table of edges and refusals is in `site#c-sweettalk-contexts`; `SweetTalk.context_map` returns the edges and states their four kinds.
3. **A call is a reference.** In context A, `B.verb`, a call on another context's module such as one of its services, counts as naming `B::`: it compiles where A follows B or inside `border B`, and in a border it draws a dependency edge (`site#c-sweettalk-contexts`).
4. **An edge nothing uses does not compile.** `follows: B` in context A is used when A's text, or a border of A other than `border B`, names `B::` or calls `B.verb`. A process step's event and a border's own text do not count: neither needs the edge. `shares: K` in a context or kernel is used when its text or one of its borders names `K::`; this check runs after the count of each kernel word's sharers. The context map refuses an unused edge at the line of the context that declares it, and the messages are in `site#c-sweettalk-contexts` and `site#c-sweettalk-kernel`.
5. **Edges stay declared.** Nothing infers `follows:` or a unit's `locks:` and `changes:` from the text. The run-time `Boundary` of [ADR 0046](0046-transactions.md) stays the check of `changes:`.
6. **A context may name its subdomain.** `subdomain:` on `context` takes `:core`, `:supporting` or `:generic` and is optional. It changes no rule. Every glossary term carries its context's subdomain (`site#c-sweettalk-subdomains`, `Term`).
7. **A context may publish a language.** `publishes` lists the context's types, services, units and calculations that other contexts may name. Once a context publishes, every other context, a follower or a border alike, names only those and the publisher's events. Every event stays nameable by any context that may name the publisher. A context that does not publish keeps the rules above. What a name publishes, where the refusal points and the one block that holds `publishes` are in `site#c-sweettalk-published` and `site#c-sweettalk-files`.
8. **A border may face a system outside the program.** `border Cards, outside: "…" do … end` declares a module `Cards` in the context and an `outside` edge in the context map. It is the only code in the context that may name `Caramel::Outbound` or `HTTP::Client`. The glossary lists the system with kind "outside", and anything but a string literal for `outside:` does not compile. The border holds no `whenever` or `compensate`. The check reads the code as written, and its other refusals are in `site#c-sweettalk-outside`. A command, a factory or a unit body does not name the border's module: outside systems stay out of a body a preview can run, a rule of [ADR 0060](0060-preview-and-commit.md).
9. **A kernel is part of a model that named contexts share, and both sides say it.** `kernel Money, shared_by: [Pricing, Billing], means: "…" do … end`, in a module that includes `SweetTalk`, declares a module that holds `value` and `aggregate` declarations; an aggregate keeps its entities, events, commands, factories and queries. `shared_by:` is a list of two or more different names of contexts or kernels. Each sharer says `shares:`, naming kernels declared before it whose `shared_by:` lists it. A kernel takes no `central:`, `subdomain:` or `renamed_from:`. The refusals are in `site#c-sweettalk-kernel`.
10. **Only sharers name a kernel.** A sharer names the kernel's types anywhere, runs its aggregates' commands and reacts to its events. No other context or kernel names, follows or borders it. A kernel names no context and reaches neither `Caramel::Outbound` nor `HTTP::Client`. The context map draws a `kernel` edge from each sharer to the kernel. A kernel edge is not a dependency edge, and a kernel shares only kernels declared before it, so sharing never runs in a circle (`site#c-sweettalk-kernel`).
11. **Every word of a kernel is shared.** Each value or aggregate of a kernel that no other word of the same kernel uses is named by two or more of its sharers, or the kernel does not compile and the message names where the word belongs. The check reads the code as written (`site#c-sweettalk-kernel`).
12. **A kernel stores like a context.** Its module includes `SweetTalk::BoundedContext`, so its tables and channels take its name. With tenancy its rows belong to the tenant, as the rows of a context without `central: true` do under [ADR 0033](0033-framework-boundary.md). The glossary lists each kernel with kind "kernel", as the context of its values, aggregates and events (`site#c-sweettalk-kernel`, `kernel`).
13. **`SweetTalk.report` is the detailed glossary.** It returns each glossary term, in the glossary's order, as a `SweetTalk::Entry` with the facts its declaration holds. `SweetTalk.glossary` lists the terms without them. The facts are listed on `Entry`.
14. **The application answers `glossary`, and Frappé prints it.** The application binary answers `glossary` with the report and the context map as one JSON document, as it answers `schema` ([ADR 0008](../0008-migrations.md)) and `requirements` ([ADR 0035](0035-reads-and-rules.md)). `frappe glossary [--json]` and `frappe contexts [--mermaid]` are rows of the command table of [ADR 0013](../0013-frappe.md), which states how such a command asks the compiled application. Frappé keeps the document in `.caramel/glossary.json` with the source signature it read, and an unchanged source answers from it. `glossary` prints Markdown and `--json` the document; `contexts` prints each context and kernel with its edges and `--mermaid` a flowchart (`site#c-sweettalk-glossary`, `site#c-commands-frappe`, `Caramel::Frappe::Glossary`).
15. **Checks.** Each refusal of subdomains, published languages, outside borders and kernels has a fixture in `sweet-talk-compilation`. `spec/sweet_talk` runs a domain that uses a subdomain, a call as a reference, a published language and an outside border against PostgreSQL, with the outside system faked by `Corretto.stub_wire`. It runs the tea house's `Calendar` and `Money` kernels against PostgreSQL, with a kernel's day in a `date` column, optional, carried in an event and read in a range. `spec/sweet_talk_tenancy` runs a tenanted kernel.

## Reasons

- Reacting to an event depends on its fields, not on the publisher's model. Counting only dependency edges lets contexts react to each other while their types point one way.
- A module method call is a dependency as much as a type name. Leaving it out lets a context reach another with no edge, so a cycle of calls compiles.
- A compiled context map exists to turn drift into compile errors ([ADR 0030](0030-scope-and-modules.md)). An edge nothing uses is drift, and it can trip the cycle check for a dependency that is gone.
- The unused-edge rule reads the same text as the refusals of a foreign name, so it needs no types and no tool.
- `follows:` is a strategic choice that publishing and borders build on; a declared edge stays in the context's head, where a reader looks.
- Rejected: a warning, or listing unused edges in a report. A warning scrolls past; the build is where SweetTalk keeps the map true.
- Rejected: inferring `follows:` from the text. It would hide the dependency from the context's head, the reason `shares:` sits on the sharer.
- A typed checker over the compiler's call graph was measured and not adopted: its walk is path-insensitive, so a branch a run-time flag never takes adds an aggregate the unit does not change. Deferred: inferring `changes:`, which waits for a front-end.
- Distillation tells a reader where modelling effort pays. It stays a label, because no check can measure how carefully a core domain is modelled, and optional, because a label is not worth failing every existing domain.
- `subdomain:`, not `kind:`, because `Term` already has `kind` ("context", "value", …) and models carry `SWEETTALK_KIND`; one word for two ideas would make the glossary ambiguous.
- Rejected: rules that depend on the subdomain, such as more checks for the core. None measures what it claims.
- In one binary an open-host service is a set of calls, and its published language the types they take and return. Listing both in one word makes the upstream's promise a compile-time fact: it can change everything else without breaking a follower.
- Events stay open to every context that may name the publisher, because a follower reacts to them and reacting depends on an event's fields.
- The published-name check runs where the names are written when it can, so the message names the line, and falls back to the whole-program check for a publisher declared later.
- Rejected: `publishes:` on `context`. The word inside the body sees the names declared before it, so a misspelt name is refused at its line.
- An outside system's answers are another model. Confining HTTP to a border makes the translation the only place where it can leak in, and lets a spec fake the system at the wire, as Corretto requires, without touching the domain.
- An outside border holds no `whenever` or `compensate` because an outside system emits no events; a webhook arrives through an action, which runs a command.
- Rejected: a partnership word. Two contexts that depend on each other form the cycle the context map refuses; partners react to each other's events, which the map already allows.
- Rejected: RPC or HTTP export of a context. Contexts are modules in one binary.
- Rejected: a small context that several contexts follow, in place of a kernel word. It shares a model, with a dependency edge each, and leaves joint ownership a team practice, not a type. Following is one-way: the followed context owns the model and nothing records who must agree to a change, so two joint owners put the model in one of them or keep two copies that drift.
- A closed list on the kernel makes joint ownership a compile-time fact: a context that starts to use the kernel edits it, where every owner reviews the change.
- `shares:` on the sharer keeps its dependencies in its head, beside `follows:`.
- Aggregates and events belong in a kernel because what two contexts must agree on often has a lifecycle. Services, policies, projections and processes act for one context, so a sharer holds them.
- A kernel that shares an earlier kernel lets kernels split by who uses them, a calendar apart from money, without merging them or copying a value; declaration order keeps that sharing acyclic.
- A list of sharers says who owns a kernel, not that each word is shared. Counting who names each word keeps one context's word out of a kernel and says where it belongs.
- Including `BoundedContext` reuses tables, tenancy, queries and their checks; a kernel differs from a context only in the words its body holds and in who may name it.
- `shared_by:` takes a list literal, as `carries:` does.
- Rejected: one side only. `shared_by:` alone hides the dependency from the sharer's head; `shares:` alone lets any context join, which is `follows:` again.
- Rejected: independent kernels. A value of one kernel that needs another's, such as a voucher's expiry day, would force the two to merge or the value to be copied.
- Rejected: checking only that each sharer names the kernel. It misses a word only one sharer uses.
- Rejected: `context Money, kernel: true`. A kernel holds fewer words and is named by other rules; one word per idea keeps each refusal precise.
- Rejected: a central kernel. A kernel is shared between contexts, not between tenants; `central:` stays a context's word.
- A report derived on demand is correct by construction; a committed copy would drift.
