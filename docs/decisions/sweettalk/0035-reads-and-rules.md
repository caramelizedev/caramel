# ADR 0035: SweetTalk declares its reads and its rules once, and the compiler checks each whether or not anything calls it

Date: 2026-10-13

Status: accepted.

## Context

A rule such as "a sealed jar still on the shelf" is written once as a `never` or a guard and again in the `where:` of each query that looks for it, and the copies drift. A read that only compares attributes makes an application that needs the newest orders, a count or a page load every aggregate, or reach into `Rows` from outside its contexts. A query checked inside its method compiles until something calls it.

A total is the first question a report asks. Without a declared read it is a projection kept current by `whenever`, a sum in Crystal over the rows a `finds` returns, or `SugarORM.sql` outside the context with the tenant predicate written by hand, where a forgotten `WHERE account_id` adds every tenant's rows together with no error ([#249](https://github.com/caramelizedev/caramel/issues/249), after [#133](https://github.com/caramelizedev/caramel/issues/133) and [#169](https://github.com/caramelizedev/caramel/issues/169)).

A team that answers to numbered acceptance criteria writes each id in a comment beside the rule and in a spreadsheet beside the spec. Nothing says which criteria no rule or example answers, and a renamed id leaves both comments wrong ([#264](https://github.com/caramelizedev/caramel/issues/264)).

A calculation that splits, rounds or converts has an identity: the parts sum to the whole, and a full settlement consumes the full balance. A `service` opens a transaction, so a pure function has no word, and its identity lives in prose and in hand-written spec loops.

## Decision

The rules an application relies on are stated on the website ([site.html](../../../website/source/site.html)), chiefly its SweetTalk guide, in the sections cited below by anchor, and in the doc comments under [src/caramel/sweet_talk](../../../src/caramel/sweet_talk), chiefly `queries.cr`, `calculation.cr` and `requirements.cr`. This record states what was chosen.

1. **A specification states a rule once, and Crystal and PostgreSQL both read it.** `specification OnSale, on: Jar, where: {…}, means: "…"` in a context is a rule and a glossary entry of kind `specification`. Its `where:` is evaluated when the rule is asked, and specifications join with `&`, `|`, `!` and parentheses. PostgreSQL reads the rule as a SugarORM condition (`SweetTalk::Specification`), which a query adds with `where_condition` ([ADR 0007](../0007-sugarorm.md)). What `where:` takes, the predicate and `satisfied_by?` it adds, `satisfying:` and how `!` reads a NULL column are in `site#c-sweettalk-specifications` and the doc comment of `specification`.
2. **The aggregate is its own repository, and its reads are declared queries.** `finds` returns aggregates and `counts` returns how many, in one statement. Their options, what each compares and their order are in `site#c-sweettalk-queries` and the doc comments of `finds` and `counts`. How a day, a decimal or a JSON document compares, ranges and orders in a query or a specification is in [ADR 0040](0040-values.md).
3. **A `finds` with a block is the escape hatch.** The block is one expression that narrows rows already scoped, and the aggregates are built from its result. It names neither `Rows`, nor SugarORM, nor its `Repo`. The calls it may make are in `site#c-sweettalk-queries`.
4. **A projection or a process declares queries too.** It declares `finds`, `counts`, `sums` and `groups` over its own attributes and its key, with `order:`, `first:` and the block; a process takes `state:` too. Neither takes `satisfying:`, and every row is live (`site#c-sweettalk-projections`, `site#c-sweettalk-processes`). A query named `all`, `new` or `allocate` on either does not compile.
5. **Every query is checked whether or not anything calls it.** A specification is checked where it is declared. Every `finds`, `counts`, `sums` and `groups` is checked once the program's top level is complete, so a query may name a specification that a later block of its context declares ([ADR 0030](0030-scope-and-modules.md)). A derived value in a query, or a query named like a repository method, does not compile; the other refusals are in `site#c-sweettalk-refusals`.
6. **Only the aggregate, projection or process builds itself from rows.** Its loader is protected (`__sweettalk_rows`).
7. **`sums` and `groups` are declared like `counts`, on first-level attributes.** They are declared on an aggregate, a projection or a process. `of:` and `by:` name an attribute of the model or of an entity the aggregate holds directly, never one below the first level. Conditions on the entities a sum adds up take what the aggregate's own take but `state:`. The forms of `of:`, `by:` and `where:` are in `site#c-sweettalk-queries`, the doc comments of `sums` and `groups`, and the recipe at `site#c-sums-choices`.
8. **A sum comes back as the attribute's type.** A sum no row matches is the zero of that type, built the way every sum is. `groups` returns `Array(NamedTuple(by: K, total: T))`, `K` the key's type with `?` when the attribute is optional; which keys have a row is in the doc comment of `groups`. `by: :id` keys are the aggregate's `Id`. An amount adds up as the money module's rule for sums says ([ADR 0063](0063-money.md)).
9. **`of:` takes only what a sum cannot break, and `by:` only a one-column key.** A value is summable when its lower bound is absent or 0 and its upper bound is absent. An amount is summable, and as `by:` it groups by its currency ([ADR 0063](0063-money.md)). A `Float64`, a `Time`, a JSON document, a value with parts other than an amount, a record or a list of entities has no one-column key and does not compile as `by:`. The summable and groupable types are in the doc comments of `sums` and `groups`.
10. **Each sum is one statement through SugarORM, with no join.** `sums` reads `sum_text` and `groups` reads `group_sum_text`, each over the query's conditions, the tenant's included; a sum of an entity's attribute narrows the entity's rows with `where_in(:parent_id, rows)` over the aggregate's conditions ([ADR 0052](../0052-sugarorm-conflicts-and-reads.md) states the three). An entity's conditions narrow its rows after `where_in`, a list as `= ANY`, and `by: :id` groups by the entity's `<aggregate>_id`. The generated method builds the type from the text PostgreSQL returns. Groups come back ordered by the stored key, so a `one_of:` value or a state comes alphabetically, not in declaration order. What stays excluded is in `site#c-sums-journal`.
11. **A sum past its type raises.** `to_i32` on an `Int32` column raises `OverflowError`, `to_i64` past `Int64` raises `ArgumentError`, and a decimal value refuses a total past its precision; none is caught.
12. **`sums` and `groups` add up one stored attribute by one key.** Neither takes a derived value in `of:`. A `finds` or `counts` takes no condition on a list of entities. The rest of what they leave out, and what to write instead, is in `site#c-sweettalk-limits`.
13. **`requirements` lists the ids a domain module answers to.** It sits in the module that includes `SweetTalk`, before its first context. The shape of an id, the refusals and `SWEETTALK_REQUIREMENTS` are in `site#c-sweettalk-requirements` and the doc comment of `requirements`.
14. **`assures:` names the ids a line answers.** `never`, `always`, `specification` and `unit` take it, and so does a `never` or an `always` in a unit's or a calculation's body (`site#c-sweettalk-requirements`). A `warn` line takes none ([ADR 0060](0060-preview-and-commit.md)).
15. **`SweetTalk.declared_requirements` returns each id with the lines that assure it.** It is read at compile time, and `SweetTalk.boot` calls it. Its order and what it returns are in the doc comments of `SweetTalk.declared_requirements`, `Requirement` and `Assurance`.
16. **`frappe requirements [ID]` asks the application.** Frappé compiles the application and runs its `requirements` command, which SweetTalk registers; the command's place in the command table is in [ADR 0013](../0013-frappe.md). `requirements --ids` prints the ids alone. An application that does not require `caramel/sweet_talk` answers with its usage, and Frappé says it declares none. The output and the exit status are in `site#c-sweettalk-requirements`.
17. **A full `frappe corretto` run fails on an id no example names.** The run is Corretto's ([ADR 0010](../0010-corretto.md)); the ids are the application's. An example names an id by holding it as a token in its description, the groups' and the example's own joined by spaces. A run of chosen paths checks nothing (`site#c-corretto-run`).
18. **A calculation is a typed function of a context that changes nothing.** `calculation verb(arg : Type, …), returns: T, means: "…" do … end` declares `Context.verb`, with no transaction, repository, event or command, timed by nothing. `publishes` may name it. Its body is typed whether or not anything calls it, as every body is ([ADR 0030](0030-scope-and-modules.md)). The glossary kind and the refusals are in `site#c-sweettalk-calculations`, `site#c-sweettalk-refusals` and the doc comment of `calculation`.
19. **Its body reaches nothing, as far as its text shows.** The names and calls that do not compile, each at the line that does it, are in `site#c-sweettalk-calculations`.
20. **A `never` or `always` line in its body is a rule on `result`.** The rules run after the body, in the order written, over `result` and the arguments.
21. **A broken rule is a defect: `SweetTalk::Broken`.** It is not a `SweetTalk::Refusal`. A calculation refuses an input outside its domain by raising `SweetTalk::Refusal` in its body, before any rule runs. What `Broken` carries and how an action answers it are in `site#c-sweettalk-calculations` and the doc comment of `SweetTalk::Broken`.
22. **`SweetTalk.calculations` returns each calculation.** It is read at compile time from `SWEETTALK_CALCULATION_<NAME>` constants, as the glossary is (`SweetTalk.calculations`, `SweetTalk::Calculation`).
23. **Corretto runs a calculation's rules on generated cases.** `Corretto.property(Context.verb)` is Corretto's runner ([ADR 0010](../0010-corretto.md)), and its cases come from what the calculation's argument types declare. What each value type draws, that a case refused with `SweetTalk::Refusal` is skipped and a broken rule on `result` fails the example, the count of cases and the seed are in `site#c-corretto-properties` and the doc comment of `Corretto.property`. `spec/sweet_talk/calculations_spec.cr` runs it on the lots: the careless split breaks its rule within the 200 cases, and the same seed fails the same way twice.
24. **Checks.** Each refusal above has a fixture in `sweet-talk-compilation`. `scripts/check integration` reads each specification the rules spec lists both ways on the same stored rows and compares the results. `spec/sweet_talk/calculations_spec.cr` runs the lots' calculations: a rule that holds, one that breaks, a refusal, a `never` line, and a broken rule inside a service that rolls back its write.

## Reasons

- One declaration read two ways states a rule once: both readings come from the same keys, and the specs compare them on stored rows. A predicate block and a query block state it twice, and a check that compares them passes on data that lacks the case where they differ.
- `where:` stays declarative. PostgreSQL cannot read a rule over entities or a derived value, so such a rule stays a `never` or a method, and no SQL enters a rule.
- `!` as `NOT` would drop the rows whose column is NULL, which Crystal keeps.
- Evans's repository offers roots only, by criteria named in the domain, as a collection. The aggregate with `find`, `all`, `finds` and `counts` already does, so a separate word would add nothing and rename every call site.
- A page needs an order, a limit and a count; without them `all` loads every aggregate to count them or show twenty.
- A caller reads `Order.newest(3)` alike whatever backs it. The block starts from rows already scoped and its result always goes through the loader, so it cannot forget a removed row or return rows instead of aggregates. Allowing only narrowing calls keeps it a read.
- A wrong query must not compile. A check inside the query's method waits for a call, so each query is checked once the program's top level is complete.
- `where_condition` is its own SugarORM method ([ADR 0007](../0007-sugarorm.md)) because another `where` overload turns "no parameter named" into "no overload matches".
- A total is the first read a report asks for, and it belongs beside `finds` and `counts` with the same `where:`, so the tenant predicate and the removed rows are handled once, by the query, not by every report.
- Text keeps a PostgreSQL sum exact without a Crystal type per column pair: `sum(int)` is a `bigint`, `sum(bigint)` and `sum(numeric)` are `numeric`, and only the caller knows which value to build.
- A sum of values each at least 0 is at least 0, so that bound holds, while an upper bound or any other lower bound can be broken by the sum. A bound that a sum can break would make a declared query raise on data it was declared for; refusing the declaration keeps a `sums` total.
- Conditions on an entity's rows go under the list's name: Crystal reads `{lines: {segment: s}}` as a named tuple and does not parse `{Line.segment: s}`, and the name is the one `has lines : Array(Line)` gives.
- An entity's row holds its aggregate's id, so a total per aggregate needs no join; the rejection of grouping by an aggregate attribute stands for every other one.
- A report that reaches another aggregate's attribute, such as an account's kind, asks that aggregate's query for the ids and passes them as a list: a statement reads one aggregate's rows.
- A sum is linear: the total of `credit - debit` is the total of `credit` less that of `debit`, exactly. A `groups` returns each key once in key order, so its keys are the distinct list, and a condition on totals is a `select` over its rows.
- A requirement is a promise; one nothing assures, or no example proves, is a promise no one is keeping. The check belongs where both are known: the compiler sees the rules, and the full run sees the examples.
- Naming the id in the example, as in `it "refuses an unbalanced entry (AC-12)"`, costs one word, and the id then shows in every spec report.
- A full run is where "no example names it" is true; a run of one file would fail every id its neighbours name.
- `requirements` is the macro that declares the ids, so the method that returns them has another name.
- A rule on a result is still a rule, and rules are core in the module split of [ADR 0030](0030-scope-and-modules.md): a domain with no money still splits and rounds.
- A service opens `SugarORM::Repo.transaction`; a function that reads nothing must not take a connection to say so.
- The caller did nothing wrong when a calculation breaks its own rule. A refusal answers 422 and tells the user to change the request, which would not help; a defect answers 500, rolls back and is reported, so the author sees it.
- A refusal in the body keeps its meaning: the input lies outside the domain, and the caller may say so to the user.
- A command needs an aggregate, which a calculation can neither take nor load. Refusing aggregates as arguments keeps every command out of reach of the text check, which cannot see a receiver's type: a calculation takes what it needs from an aggregate, or its id, and the caller loads it.
- No span: a calculation may run inside a loop of thousands, and the command or service around it is timed already.
- A Crystal body, not an expression language: expression bodies are a decision of their own for the whole language, and a calculation needs nothing a typed function lacks.
- A property case runs the real calculation on inputs no one chose, which an example cannot: the generators come from the constants the value macros already record, so a case needs no hand-written generator. A refusal skips the case, because the domain said the input lies outside it; only a broken rule is the calculation's fault.
- The runner needs no database, so it lives in Corretto beside the other spec helpers and runs in any example; a fixed count and a printed seed make a failure repeatable.
- **Rejected: a storage block that may name `Rows`.** Its read-only rule would be a text check, and its queries could forget removed rows.
- **Rejected: parameters on a specification.** A `finds` takes arguments and adds a specification.
- **Rejected: SQL in a declared read.** SQL stays out of rules, as for a specification; `where_in` says the join without naming a table or a column.
- **Rejected: typed SugarORM sums.** An overload per column type and per key type, when one text terminal and one conversion per declaration do the same.
- **Rejected: grouping an entity sum by an aggregate attribute.** It needs a join in the group key; a `where:` on the aggregate attribute reads the same total.
- **Rejected: conditions written `Line.segment:`.** Crystal does not parse them.
- **Rejected: a join through a reference, `Line.account.kind`.** It reads another aggregate's columns, which `Rows` keeps private ([ADR 0039](0039-aggregates.md)).
- **Rejected: `of:` an expression or a derived value.** It states a Crystal expression again in SQL, which the specification rule keeps out.
- **Rejected: a `distinct` word and `having:`.** Each is a `groups` read another way.
- **Rejected: a comment beside the rule.** Nothing reads it.
- **Rejected: tags on the example.** The description is what a failure report shows, and one more syntax is one more place for a renamed id to go stale.
- **Rejected: checking a partial run.** It would make `frappe corretto path` fail on requirements it was not asked about.
- **Rejected: `service` for calculations.** It opens a transaction and may change an aggregate.
- **Rejected: a broken rule as a `Refusal`.** It would answer 422 and blame the request for the calculation's fault.
- **Rejected: checking a calculation's rules only in specs.** A rule that holds in every example and breaks on one production input would then compute a wrong number silently.
- **Rejected: rules outside the body.** They read `result`, which exists only after it, and a rule in the body sits beside the code that must keep it.
- **Rejected: a plain-`spec` helper in `caramel/sweet_talk/spec`, or `frappe check properties`.** The first splits spec helpers across two products; the second runs specs outside `frappe corretto`, and its workers' settings.
- **Rejected: shrinking a failing case.** The case, its seed and its arguments are printed; the arrays hold at most 8 elements, so a failure reads as it is.
