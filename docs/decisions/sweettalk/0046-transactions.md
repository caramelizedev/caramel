# ADR 0046: A SweetTalk command is one transaction on one aggregate, and a unit is one transaction that locks the aggregates it names first

Date: 2026-10-08

Status: accepted.

## Context

A domain changes state in transactions, and something must say what one transaction may change. The DDD Reference draws that line at the aggregate. A domain also needs operations that belong to no one aggregate.

Two aggregates that must change together, such as a journal and the positions it posts, had one seam: two commands called in turn inside one `SugarORM::Repo.transaction`, each a savepoint. The seam was supported but unnamed. It took each row's lock in the order the code happened to call it, so two callers could deadlock, and it checked the invariants of each aggregate alone, so no rule could span the set. An application that built its financial layer on it wrote its own `Books.unit` around the seam, with hold commands that locked each aggregate first.

A client that retries a request must not move money twice. A unit that posted a transfer ran again for each retry, and an application kept its own claims table, written in the same transaction, with the fingerprint of the request and what it answered, one per unit ([#261](https://github.com/caramelizedev/caramel/issues/261)).

A refusal reached a form under `_base`, so an application mapped sentences back to fields by comparing strings.

## Decision

The rules an application relies on are stated on the website ([site.html](../../../website/source/site.html)), chiefly its Domain-Driven Design guide, in the sections cited below by anchor, and in the doc comments under [src/caramel/sweet_talk](../../../src/caramel/sweet_talk). This record states what was chosen. Aggregates and their `never` and `always` rules are [ADR 0039](0039-aggregates.md)'s, events and their dispatch [ADR 0041](0041-events.md)'s, and running a body dry and committing it against what a person saw [ADR 0060](0060-preview-and-commit.md)'s.

1. **A command is one transaction on one aggregate.** `to verb(arg : Type) do … end` in an aggregate runs in `SugarORM::Repo.transaction`: it locks the root's row and loads the aggregate, runs the body, checks every `never` and `always`, saves the root, then its entities, and dispatches the events. A `SweetTalk::Refusal` rolls it back, and the aggregate reloads what is stored. A command or a `create` on another aggregate while a command runs raises `SweetTalk::Boundary`, as does a command on a second aggregate in a `whenever` handler, or a unit called inside a command. The guard runs at run time, on the fiber. `to finalize` does not compile. The steps and each outcome are in `site#c-sweettalk-commands`.
2. **`refuse` ends a command, and a refusal may name its field.** `refuse "message"` raises `SweetTalk::Refusal`. `refuse "…", on: :tins`, and `on:` on `never`, `always` and the rules in a unit's body, set `Refusal#on` to `"tins"`; a service raises `SweetTalk::Refusal.new("…", on: :tins)`. An `on:` that is not a symbol does not compile (`site#c-sweettalk-commands`, `site#c-sweettalk-screens`, `SweetTalk::Refusal`). How an action answers a refusal, and under which field, is [ADR 0033](0033-framework-boundary.md)'s.
3. **A service is one transaction that changes at most one aggregate.** `service verb(args), returns: T, means: "…" do … end` in a context is a domain service and a glossary entry. It changes at most one aggregate by any number of commands, a `create` or a factory counting as the first, or runs one unit; a command on a second aggregate raises `SweetTalk::Boundary`. Anywhere but a context it does not compile (`site#c-sweettalk-services`). A context's own event, which only a service body emits, is [ADR 0041](0041-events.md)'s.
4. **Two commands in one transaction are a supported seam.** Two commands called in turn inside one `SugarORM::Repo.transaction`, each a savepoint, commit and roll back together, and `spec/sweet_talk` proves it. A unit names that seam and locks first.
5. **`unit` is a declared word.** `unit post(journal : Journal::Id, segments : Array(Segment::Id)), changes: [Journal, Position, Segment], locks: [journal, segments], returns: Nil, means: "…" do … end` in a context declares `Ledger.post`: a glossary entry with kind "unit" and a `domain` span named `Ledger.post`. `changes:` lists the aggregates its commands may change, `locks:` names the arguments whose rows it locks first, and a `never` or `always` line in its body is a rule over the set, run after the body. `publishes` may name a unit as it names a service. Every option with its default, and each declaration that does not compile, are in `site#c-sweettalk-units`, `site#c-sweettalk-refusals` and the doc comment of the `unit` macro; `assures:` on a unit and on its lines is [ADR 0035](0035-reads-and-rules.md)'s.
6. **A unit is one transaction, locks first.** It runs in `SugarORM::Repo.transaction`: it locks the rows `locks:` names, runs the body, runs its `never` and `always` lines, and commits. Each command inside it is a savepoint that dispatches its own events, and the unit pins one flow for them. A refusal, a boundary or any other error rolls the whole unit back, every aggregate instance its commands touched reloads what is stored, and the error goes on (`site#c-sweettalk-units`). Inside `SweetTalk.preview` it runs dry, by the rules of [ADR 0060](0060-preview-and-commit.md).
7. **`SweetTalk.lock` is the ordered lock.** `SweetTalk.lock(*ids)` takes ids, aggregates and arrays of either, groups them by table and locks each table's rows in one statement, in id order, through the aggregate's rows query, so the tenant predicate applies; the tables go in name order. It is re-entrant: a row locked twice is held once. A call after a unit's own is ordered within its own batch only. An entity's or a record's id is not lockable. The statement, and what a missing row and a call outside a transaction raise, are in `site#c-sweettalk-units` and the doc comment of `SweetTalk.lock`.
8. **A unit's commands keep to its list and its locks.** A command or a `create` on a type outside `changes:` raises `SweetTalk::Boundary`, and so does a command on an existing row of an allowed type that `lock` did not take; a row created inside the unit needs no lock. A command on another aggregate while a command runs is refused inside a unit as it is outside one. The messages are in `site#c-sweettalk-units`.
9. **A unit runs where one change may run, and is that change.** Inside a command, a factory or another unit it raises `Boundary`. Inside a handler or a service it is allowed only while that handling has changed nothing, and then it is the handling's one change: a command or a second unit after it raises `Boundary` with the handling's own message. The fiber keeps one handling object, `SweetTalk::Handling`, with what it changed, an aggregate or a unit. Who may call a unit is listed in `site#c-sweettalk-units`; compensations, deadlines and process steps are [ADR 0031](0031-processes.md)'s.
10. **Crossing rules apply to a unit's text.** Naming another context's aggregate in `changes:` needs `follows:` or `shares:`, and the published and border rules that the context macro and the context map check ([ADR 0036](0036-strategic-design.md)) apply to the unit's text. A central context's unit may not change a tenanted aggregate; that does not compile.
11. **`SweetTalk::Unit` is the running unit.** The declared word has a class of its own, which holds the unit's list, the rows it locked or created and the instances its commands touched (`SweetTalk::Unit`). The row batch of a projection's or a process's handler has another name, `SweetTalk::Work` ([ADR 0041](0041-events.md)).
12. **`once_by:` makes a unit run once per operation key.** `unit post(key : String, …), once_by: key` names one argument, a `String` or a value that wraps `String`. The unit's name and that key are the operation.
13. **A repeat replays the first outcome, and a repeat with other arguments is refused.** The unit keeps a fingerprint of every other argument, as SHA-256 of the arguments packed as JSON in declaration order. A repeat with the same fingerprint skips the locks, the body and the rules and answers the first outcome: nil for a unit that returns `Nil`, otherwise what `returns:` unpacks from the stored JSON. A repeat with another fingerprint raises `SweetTalk::Refusal` with the sentence `otherwise: "…"` gives, or "<Context>.<unit> already ran under this key with other arguments". `otherwise:` without `once_by:`, or as anything but text, does not compile (`site#c-sweettalk-units`).
14. **The operations table is derived, and its rows are kept forever.** A context with such a unit has `<context>_operations`, `Rows::Operations`: an `Int64` id the database assigns, whatever the domain's id type, then `unit`, `key`, `fingerprint`, `outcome` jsonb and `created_at`, with a unique index over `unit` and `key`, tenanted as the context's rows are, so each tenant has its own keys. `frappe db diff` creates it. A declaration whose table it would take does not compile. Nothing prunes the table.
15. **The claim is the first statement in the unit's transaction, and rolls back with it.** The claim is an insert in a savepoint. A key already claimed raises `UniqueViolation` or `Invalid`, which rolls back that insert alone and leads to reading the row. A concurrent first run holds the second on its uncommitted row, until it commits and the second replays it, or rolls back and the second runs. A refusal or an error leaves no row, so a retry runs again. The outcome is written after the rules pass, in the same transaction.
16. **What a unit that runs once keeps is plain.** The other arguments and the result hold ids, values and scalars: an aggregate in either does not compile.
17. **Every refusal has a fixture, and the units run against PostgreSQL.** Each refusal above that stops compilation has a fixture in the `sweet-talk-compilation` check. `spec/sweet_talk/units_spec.cr` runs the shelf's units against PostgreSQL: two boxes committed and rolled back together with both instances reloaded, a set rule refused, a type outside `changes:` and an unlocked row refused, a created row unlocked, two connections running one unit on the same boxes in opposite order, a unit as a service's one change, a unit refused inside a command and inside a unit, and `lock` refused outside a transaction.
18. **Each command, factory, `create`, service and unit is a `domain` span.** Crema ([ADR 0027](../0027-crema.md)) times each as a `domain` span named after it, such as `Ordering::Order#place` or `Ordering.requote`, with no detail and no counter; a refusal sets its `error_class` (`site#c-sweettalk-commands`, `site#c-crema-work`).

## Reasons

- The DDD Reference governs transactions by aggregate boundaries and updates across them asynchronously. One aggregate per transaction keeps each lock and each invariant its aggregate's own. A reference that yields an id makes a value needed at one moment, such as the price at checkout, an attribute captured then. The guard runs at run time, because a call's receiver type is unknown when a macro expands.
- The row lock orders commands on one aggregate so each sees the last one's result, where a version column would fail the later one.
- Rejected: restoring an in-memory snapshot after a refusal. Inside savepoints, only the database is certainly right.
- One aggregate per transaction holds for a service as it does for a command.
- A refusal from `never` or `always` reaches the same `render_refusal` as one from `refuse`, so every line that raises one takes the same keyword.
- Rejected: a field chosen by a rule's identity. `on:` names it where the rule is written.
- A declared word names the seam: the glossary lists what changes together, and the context map's text checks read `changes:` like any other naming.
- Locks taken first, by table then id, in one statement per table, give every caller one order whatever its arguments' order, so two units on the same rows wait instead of deadlocking; `ORDER BY id FOR UPDATE` locks rows as PostgreSQL returns them.
- Listing `changes:` keeps the unit as narrow as a command: a command on a type the unit did not declare is a stray write, and a command on a row it did not lock would take that lock late, after the body already read the row.
- A set rule after the body runs over the aggregates as the commands left them, within the same transaction, which no single aggregate's `never` can see.
- Reloading every touched instance after a rollback keeps the rule set for one command: inside savepoints, only the database is certainly right.
- A unit counts as a handling's one change because it is one: letting a service run a unit and a command would make the service the seam again, without its list or its locks.
- Refusing a unit inside a command keeps a command's transaction its aggregate's own, and inside a unit keeps one list and one lock order per transaction.
- Naming the row batch `Work` costs one internal word; a public `unit` beside a private `Unit` that meant something else would mislead every reader of the runtime.
- **Rejected: locking lazily, as each command runs.** It is the unnamed seam: the order follows the code, and two callers deadlock.
- **Rejected: advisory locks.** They would not cover the row locks the commands take anyway, and would hold past the rows.
- **Rejected: a unit inside a command.** The command's row lock would be held while the unit takes others, in the command's order.
- **Rejected: taking `changes:` from the body.** A receiver's type is unknown when a macro expands; the list is the author's statement, checked at run time as the one-aggregate rule is.
- **Rejected: keeping `SweetTalk::Unit` for the row batch.** The declared word would then have no class of its own, or a misleading one.
- Idempotency belongs where the state changes: the claim and the change commit together, so there is no moment where one holds without the other.
- A fingerprint tells a retry from a new request that reused a key, which would otherwise be answered with the wrong outcome.
- A derived table named by the unit says which unit it guards, and follows the tenant.
- A unit that runs once keeps no aggregate in its arguments or result, since a replay could not build it.
- **Rejected: a hand-written claims table.** It is the workaround the derived table replaces.
- **Rejected: a key that is the fingerprint.** A client that retries with a changed field is a new request; the client's key says it is the same one.
- **Rejected: pruning operations after a time.** It would turn a retry that arrives late into a second run. A retention window would have to choose how long a key may come back, which is the client's contract.
- A `domain` span names the command a trace ran, which its SQL alone does not; it carries no arguments or ids, so production detail keeps it whole.
