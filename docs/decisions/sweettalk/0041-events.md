# ADR 0041: A SweetTalk event carries its facts and leaves through Cold Brew in the command's transaction

Date: 2026-10-08

Status: accepted.

## Context

A domain event names something that happened, and other parts of the program react to it. Several things needed a rule: what an event holds, how it reaches its handlers without being lost or sent for a rolled-back change, who acted, and how a read model keeps one row per key.

Use then showed six gaps:

- **Restated fields.** An event that tells what a transfer was when it settled declared each of the aggregate's fields with its type, and every command that emitted it passed each field again. An event of 17 fields was written as 17 declarations and 17 `name: name` arguments, and the two lists were checked only when something emitted the event.
- **Who acted.** An event did not say who acted, and a queued event could not name what caused it.
- **Order.** Jobs start in declaration order and finish in any, so a policy that needed a read model's row waited for no one: "run after Sales has saved" could not be said ([#248](https://github.com/caramelizedev/caramel/issues/248), split from [#168](https://github.com/caramelizedev/caramel/issues/168)).
- **Creation.** A factory emits the event that says what was made, so a policy follows it and an event log keeps it. `create` emitted nothing: an aggregate made with `create` was invisible to every `whenever`, to `SweetTalk.rebuild` and to an audit, and the only way to see it was to read its table ([#265](https://github.com/caramelizedev/caramel/issues/265)).
- **Older events.** A job queued before an event gained a required field could not be read: loading it raised on the missing key.
- **Sealed documents.** A journal that must show the rules it was sealed under read the rules as they are today, so a repricing changed a sealed journal's meaning; the application copied the rules into the journal by hand ([#263](https://github.com/caramelizedev/caramel/issues/263)).

## Decision

The rules an application relies on are stated on the website ([site.html](../../../website/source/site.html)), chiefly its Domain-Driven Design guide, in the sections cited below by anchor, and in the doc comments under [src/caramel/sweet_talk](../../../src/caramel/sweet_talk). This record states what was chosen.

1. **An event belongs to an aggregate or to a context, and only its owner emits it.** `event Name, field : Type, means: "…"` in an aggregate declares one of its events, and `emit Name, field: value` queues it from a command or a factory, its own only. A context's own `event` is for a change no aggregate holds: it takes no `carries:`, and only a service body may `emit` it. `renamed_from:` on an event keeps its channel and its queued jobs. The words are in `site#c-sweettalk-events` and `site#c-sweettalk-services`, and on the `event` and `emit` macros of `SweetTalk::Aggregate` and `SweetTalk::BoundedContext`.
2. **An event holds its facts as they were when it was emitted, and no getter on it loads an aggregate.** It holds its subject's id and its fields; the field types, the nilable field and the reserved names are in `site#c-sweettalk-events` and `site#c-sweettalk-metadata`. The subject's id is read when the event is dispatched, so a factory's event names the new aggregate (`SweetTalk::Event`). An entity among the facts is packed at dispatch, after the command or factory has saved, so it carries `"id"`, its row's; a scalar field keeps the value `emit` read. An entity that was never saved packs `"id": null`, and a job queued before entities carried an id has none, so `line.id` on it raises (`Aggregate#__sweettalk_dispatch_events`).
3. **`carries:` takes an event's fields from the aggregate by name.** `event Settled, carries: [kind, amount, owner], means: "…"` declares one field for each attribute or derived value named, of that attribute's type, in the order given; the names are written as words or symbols, and an optional reference is carried as `Owner::Id?`. `emit` reads those fields from the aggregate as it is when `emit` runs, and a command cannot give one. A carried field is an ordinary field: typed, stored in the event's JSON, and read back as emitted by a `whenever` and from an event log. `the` records its type, so a derived value can be carried. The refusals and the way to rename a carried attribute are in `site#c-sweettalk-metadata`; the `event` macro of `SweetTalk::Aggregate` states the rest.
4. **Every event records its id, when it occurred, who acted, what caused it and its flow, and its jobs carry them.** `SweetTalk.acting(by) { … }` names the actor of the events emitted inside it, so no command takes an actor, and each policy, compensation and process step runs as its event's actor. `cause_id` is the `event_id` of the event whose handler emitted it, or whose step armed the deadline that did. A retried job restores the same `event_id`, the key a handler gives a side effect outside PostgreSQL. What each of the five holds, and where a flow comes from, is on `SweetTalk::Event`, `SweetTalk.acting` and `SweetTalk.__sweettalk_flow`, and in `site#c-sweettalk-metadata`.
5. **`create` announces `Created`.** An aggregate without a factory has an event `Created` on `sweettalk.<context>.<aggregate>.created` that carries every attribute, in declaration order, with the types `carries:` gives them: a reference is `Agg::Id`, a record `RecordId(Agg)`, an optional attribute optional. An attribute named like the metadata or the subject's id is left out, and the glossary lists the event, meaning "<Aggregate> was created". `create` checks the invariants, inserts the root and its entities, emits `Created` and dispatches it in one transaction, as a factory does, with one flow, and the open handling or unit remembers the aggregate as the one it changed. A `create` that a `never` refuses emits nothing. A declared `event Created, carries: [member], means: "…"` is the one `create` emits, and carries those attributes only; one with fields of its own does not compile, because `create` has nothing to give them. A `Created` channel over its budget does not compile, and the message names the choice: a shorter name, or a factory, which replaces `create` and `Created`. An aggregate with a factory has no `create` and no generated `Created` (`site#c-sweettalk-commands`, `site#c-sweettalk-factories`).
6. **The command enqueues one Cold Brew job per handler, in its own transaction.** `whenever Event do |event| … end` is a policy in a context or a border, a row update in a `projection`, and a step in a process ([ADR 0031](0031-processes.md)). `SweetTalk.dispatch` enqueues one job per `whenever` that follows the event, and one per element with `each:`, each carrying the event as JSON; Cold Brew's `enqueue` joins the command's transaction ([ADR 0009](../0009-cold-brew.md)). Jobs go in declaration order: the contexts' and borders' policies, then the projections' handlers, then the processes' steps. Cold Brew starts them in that order and finishes them in any, so no handler assumes another's work saved unless it says `after:` (`SweetTalk.dispatch`, `site#c-sweettalk-events`). For specs, `SweetTalk.emitted` returns the events `dispatch` saw; `SweetTalk.preview` collects them in a dry run ([ADR 0060](0060-preview-and-commit.md)). Under `caramel/tenancy` a job runs in the tenant its event was emitted in, and a tenanted handler of a central context's event does not compile ([ADR 0033](0033-framework-boundary.md)).
7. **`after:` orders two handlers of one event.** `whenever Order::Placed, after: Sales do … end` names a projection, a process or a context that follows the same event. `dispatch` does not enqueue such a handler: the predecessor's job calls `SweetTalk.__sweettalk_release` once its body has run, inside the transaction that saves its work, and that enqueues each follower with the same subject, fields and metadata. A refused or permanently failed predecessor never releases its followers. The whole-program check runs at `macro finished` and resolves each handler's event and `after:` from the owner's scope outwards; beside the refusals in `site#c-sweettalk-events`, it refuses an owner that follows the event twice, in a border and outside it. `after:` works without an event log. `spec/sweet_talk/event_log_spec.cr` proves the ordering and the absence of followers after a failed predecessor against PostgreSQL, and the fixtures `after_not_following`, `after_cycle` and `after_each` prove the refusals.
8. **A job is named after its owner and the event, and a rename declares the old name.** The owner is a context and its border, a projection or a process, and the event is its path as written; a deadline's job is named after its process and the deadline, as `Hold::LapseDeadline`. `caramel_jobs` stores that name, so two `whenever`s for one event in one owner do not compile. When a `renamed_from:` changes the name, the job declares Cold Brew's `renamed_from` ([ADR 0009](../0009-cold-brew.md)) with the old one, from a `macro finished` in the job's body, where every name is known, so queued jobs still run. An old name that another job has or claims does not compile (`SweetTalk.__sweettalk_aliased`, `site#c-sweettalk-renames`).
9. **A refusal or a boundary fails a job at once, and any other error follows the handler's retry rule.** Each job declares `retry_on` with one attempt for `SweetTalk::Refusal` and for `SweetTalk::Boundary`. `attempts:`, `backoff:` and `base:` on `whenever`, and on `deadline`, become `retry_on ::Exception` after those two, so a literal Cold Brew refuses does not compile; without them the job follows Cold Brew's retry rules ([ADR 0009](../0009-cold-brew.md)). A failed job releases no `after:` follower (`SweetTalk.__sweettalk_retries`, `site#c-sweettalk-events`).
10. **A stored event is read as it was written.** A job that is already queued reads the JSON it holds. A field typed `T?` that a stored event lacks, because the event was emitted before the field existed, reads nil. `older: {till: "front"}` on the event gives a required field the value a queued job or a logged row without it reads; the value is evaluated each time such an event is loaded. A stored event that lacks a required field without `older:` raises when it is read. An `older:` value of another type fails compilation whether or not anything loads the event, because the whole-program checks type it as they type every body ([ADR 0030](0030-scope-and-modules.md)). The refusals are in `site#c-sweettalk-refusals`, and `spec/sweet_talk/event_log_spec.cr` and the fixtures `older_not_tuple`, `older_unknown`, `older_optional` and `older_type` prove them (`SweetTalk.__sweettalk_event`, `site#c-sweettalk-metadata`).
11. **The command publishes the subject's id, never the fields.** After the jobs, `dispatch` publishes `{"subject": <id>}` through Cold Brew's `publish` on `sweettalk.<context>.<aggregate>.<event>`, each part underscored; a service publishes its context's event on `sweettalk.<context>.<event>` with the bound tenant's id, or null, as subject. Delivery is on commit and at most once ([ADR 0009](../0009-cold-brew.md)), and the payload stays inside Cold Brew's 8,000-byte limit (`site#c-coldbrew-limits`). A channel over PostgreSQL's 63 characters does not compile; under `caramel/tenancy` it goes out behind the tenant's prefix, which shrinks the budget ([ADR 0033](0033-framework-boundary.md)). The stored channel names are listed in `site#c-sweettalk-renames`.
12. **A projection keeps one row per key.** `projection Name do … end` declares the read model, and `key name : Type` names the attribute that picks a row; the key is uniquely indexed. In a `whenever` block, `Projection[key]` reads the key's row locked; when it is absent, a SugarORM upsert that does nothing on a conflict inserts it with its defaults, and the row is read locked again. A handler's projection and process rows live in a `SweetTalk::Work` on its fiber (`Fiber#__sweettalk_work`), and each row the handler touched is saved through its changeset when the handler returns (`site#c-sweettalk-projections`, `SweetTalk.__sweettalk_work`).
13. **A context may keep its events.** `event_log:` on a context keeps every event in a table beside its rows; the log, its readers, the rebuild of a projection, retention and the walk from an event to what it led to are [ADR 0048](0048-event-log.md).
14. **`pinned_at:` copies a referenced aggregate when a state is entered.** `has rules : Setup::Rules, pinned_at: :finalized`, in an aggregate, on a reference to another aggregate, keeps the reference and a read-only copy taken in the transaction of the mover that enters the state; `pinned_rules` reads it. A command on a copy raises `SweetTalk::Boundary`, "Rules 7 is a pinned copy, read only: find Rules 7 to change it". What the copy holds, what an attribute it lacks reads, and the refusals are in `site#c-sweettalk-lifecycle` and on `has` in `SweetTalk::Model`.

## Reasons

- Enqueueing in the command's transaction is the outbox: an event is never lost or sent for a rolled-back change.
- An event records what happened. A handler that reloads its subject reads the present instead: a projection counted tins added to an order after checkout.
- A row lock cannot order the insert of a missing row, so a projection inserts it through an upsert that does nothing on a conflict.
- A notification carries an id, as Cold Brew advises: fields could pass its 8,000-byte limit, and the refused publish would roll the command back.
- **Rejected: policies inside the publishing command.** A policy's refusal would reach the client after the first change had been kept.
- `acting` keeps call sites unchanged: no command takes an actor argument, yet every event and every job that follows it knows who acted. `cause_id` and `flow_id` follow it the same way. A flow is the trace id where one exists, so a trace and its events share an id; it outlives the trace, which each job queued outside a trace starts anew.
- **Rejected: an explicit `by:` argument on every command.** Every caller would pass it, and a policy would have to pass it on.
- **Rejected: ids in log lines only.** A queued event could not name what caused it.
- The field's type and name were already written once on the attribute. Restating them in an event copies a declaration, and the copies drift. Carrying removes the copy and makes the coupling explicit, which is the trade-off below.
- Reading at `emit` time is what an explicit `kind: kind` read, so an event carries facts as they were, and a handler never loads the aggregate.
- The `carries:` list names the fields once, in the declaration that says what the event is, instead of in each command that raises it.
- A command may not give a carried field, because a carried field is the aggregate's, read when the event is emitted: an event that said `owner: nil` of an aggregate whose owner is set would be a fact the aggregate cannot show. An event that reports a change and needs the value before it declares a field of its own name, as `before_owner : Owner::Id?`.
- An entity's id exists only once the save has run, after every `emit`, and the save is in the same transaction as the dispatch. Packing entities at dispatch is the one moment the id is known and the event has not left the command; a handler that follows a line needs that id, and a line packed at `emit` would name nothing.
- **Trade-off: an event that carries is a snapshot of the aggregate.** `carries:` ties the event to the aggregate's attribute: its name, its type and what it holds. An event is stored, as JSON, in the job that delivers it to the handlers. This is a deliberate coupling: the event is the aggregate's own, and in exchange no declaration is repeated.
- Renaming or retyping a carried attribute changes the payload of jobs already queued. A job queued under the old name lacks the new field, and one queued under the old type holds a value of the old type. Nothing fails when the aggregate is compiled; the job fails, or reads nil, when a worker runs it.
- An attribute is renamed safely only when the new one is optional. A job queued under the old name holds only the old name, and the worker reads every field of the event before a handler runs, so a required field the job lacks fails it. When `owner` becomes `account : Account::Id?`, declare `the owner : Account::Id? = account` above the event, a derived value with the old name, and carry `[account, owner]`: a job queued under the old name reads `account` as nil, one queued since reads both. Drop the old name once the queue has drained. When the new attribute is required, emit a new event for the new shape and keep handling the old event until its jobs are done. `renamed_from:` renames a stored table or event, not a carried field. An optional field that a queued job lacks reads as nil, so adding a carried optional attribute is safe; adding a required one is not until the queue has drained.
- An event of 17 fields that are all the aggregate's is the case `carries:` serves. An event that should stay stable while the aggregate changes shape should declare its own fields.
- **Rejected: `emit Settled, from: self` with fields chosen at the call.** Each command would say again which fields the event has, and two commands could say differently.
- **Rejected: carrying every attribute by default.** An event is a fact about one change; what it holds should be listed, and `carries:` lists it once. `Created` is the one event that carries every attribute, because creation is the change that makes them all true.
- **Rejected: reading the aggregate in a handler.** A handler would read what is true at that moment, not what happened.
- A fact that something exists is the first fact a policy needs; leaving it to every aggregate's author to declare and emit meant most did not.
- Creation is the one change that makes every attribute true at once, so carrying all of them is the fact, and `carries:` listing each would restate the aggregate.
- Reusing the factory's making keeps one path for check, save and dispatch.
- **Rejected: an opt-in `emits_created` word.** A second way to say what `create` already does, that an aggregate forgets.
- **Rejected: shortening the generated `Created` channel.** A channel that differs from the aggregate's other events breaks the `sweettalk.<context>.<aggregate>.<event>` shape every reader relies on.
- **The predecessor enqueues its followers.** A worker-side wait would hold a fiber and cannot see a predecessor in another process; a follower enqueued in the predecessor's transaction is atomic with the work it waits for, and is never enqueued when that work rolls back, which is why a refused or failed predecessor releases none.
- **Not after `each:`.** One job per element would release the followers once per element.
- **Rejected: resolving `after:` where the handler is written.** A projection may be declared after the handler that names it, and an event of a context declared later resolves only once every name is known, so the check runs at `macro finished`.
- A default per field is the smallest thing that keeps old events readable. Spatie keeps an `event_version` and Axon chains upcasters by revision; Verbs shipped without either and its maintainers are still deciding. A SweetTalk event changes by gaining fields, which a default covers without a column; a field whose type changes is a new event, and a new name is `renamed_from:`.
- A reference names a row that changes; a document that must stay true says what the row was. A copy taken in the mover's own transaction is exact, where a copy taken by a handler would read a later row.
- **Rejected: pinning at creation.** The state is where the fact becomes true; a draft changes.
- **Rejected: a pinned copy that can change.** It would stop being what the aggregate said.
