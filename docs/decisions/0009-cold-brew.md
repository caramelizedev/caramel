# ADR 0009: Cold Brew runs jobs, schedules, PubSub and cache on PostgreSQL inside the application process

Date: 2026-09-27

Status: accepted.

## Context

An application needs background jobs, recurring tasks, notifications to open pages and a cache. Each is usually a second system beside the database, and a write that must reach both can reach only one. Several things needed a rule: how finished jobs and partitions coexist, how a least-privileged runtime role creates partitions, how notifications reach subscribers without blocking, how specs drain queues, and how the running application hosts all of this.

A signed webhook relay built on Caramel 0.4.0 ([#6](https://github.com/caramelizedev/caramel/issues/6)) then reached past the framework in four places:

- **Status.** To show a delivery's attempts, next run, lock and failure, its dashboard joined its own table to `caramel_jobs`, whose partitioning and columns belong to the framework ([#4](https://github.com/caramelizedev/caramel/issues/4)).
- **Transitions.** A failure rolls back the job's transaction, and Cold Brew then writes the retry or failure with no callback, so the dashboard polled for it ([#4](https://github.com/caramelizedev/caramel/issues/4)).
- **Processes.** A second process that only worked queues needed a custom compiled entry point to start `Worker` and `Scheduler` ([#5](https://github.com/caramelizedev/caramel/issues/5)).
- **Renames.** A job renamed or moved by a deploy left its queued rows under a class name no binary compiled, and each failed on its first run ([#72](https://github.com/caramelizedev/caramel/issues/72)).

## Decision

The rules an application relies on are stated on the website ([site.html](../../website/source/site.html)), chiefly its Cold Brew reference, in sections named below by anchor, and in the doc comments under [src/caramel/cold_brew](../../src/caramel/cold_brew). This record states what was chosen.

1. **One database.** Jobs, schedules, notifications and the cache live in the PostgreSQL that holds the application's data. Their tables are framework migrations, `Caramel::ColdBrew::MIGRATIONS` (versions `20260927000001`–`…07`), which define every column and index. Generated applications start their migration list with them, and the SugarORM differ ignores `caramel_*` tables.
2. **A job is written in the business transaction.** A job is a struct under `Caramel::ColdBrew::Job` with typed params, and `enqueue` writes its row through `SugarORM::Repo`'s current connection, so inside `Repo.transaction` it commits or rolls back with the business write. Declaration, retry rules and their lookup order are in `c-coldbrew-define`, `c-coldbrew-retry` and `c-coldbrew-enqueue`.
3. **Finished jobs leave by partition, not by row.** `caramel_jobs` is `PARTITION BY RANGE (enqueued_at)` with daily `caramel_jobs_pYYYY_MM_DD` partitions and a default partition; its primary key is `(id, enqueued_at)`. A finished row stays in its partition until the partition is dropped, so `caramel_jobs_fetch` and the other queue indexes exclude finished rows. The creation and retention windows are in `c-coldbrew-run`.
4. **The runtime role maintains partitions without schema privileges.** Partition DDL runs through two `SECURITY DEFINER` functions owned by the migration role, each with a 2-second `lock_timeout`.
5. **A worker claims with `SKIP LOCKED` on the connection that runs the job.** The claim is a `FOR UPDATE SKIP LOCKED` query over unfinished rows on a connection bound to the worker fiber, so `locked_by` is the backend that runs the job. One index matches the claim's predicate and order and one the release's; the comment on migration `…07` in `MIGRATIONS` says why they are built without `CONCURRENTLY`.
6. **Jobs run at least once.** `perform` and `finished_at = now()` share one transaction, so a job's own writes commit once, with its completion. A call to another service repeats when the process dies or the commit fails after the call; receivers deduplicate on a stable identifier (`c-practices-jobs`). A failed run rolls back and is rescheduled by its retry rule or failed; how the failure is stored, and what happens when storing it raises, is in `c-coldbrew-retry`.
7. **A dead backend's lock is released from `pg_stat_activity`, and released runs are counted apart.** Maintenance releases a lock as soon as its backend is gone, or the PID belongs to a backend started after the lock was taken. A release fires no hook and does not spend the retry rule's `attempts:`; `caramel_jobs.releases` counts it, and the third (`Maintenance::RELEASE_LIMIT`) fails the job with `AbandonedJob` and calls the `on_failed` hooks, as `Queue.run` does.
8. **Idle workers poll and are woken by the enqueue.** An enqueue's `pg_notify('caramel_jobs', queue)` is delivered on its commit and wakes the idle fibers of that queue; the one-second poll covers scheduled runs, retries and lost notifications (`Worker`).
9. **Maintenance is one idempotent pass in every process.** Every 60 s it creates partitions, releases dead locks, deletes expired cache rows and drops old partitions, each step reported on its own so one that raises never skips the rest (`Maintenance`, `c-coldbrew-run`). It runs with or without workers and schedules.
10. **A row stores a class name, and the class declares its old names.** `enqueue` stores the job's current fully qualified class name; a worker runs the compiled job of that name or the one that declares it in `renamed_from`. Conflicting claims fail compilation, including those a `macro finished` declares, as SweetTalk's jobs do. A name no compiled job claims fails on its first run with `UnknownJob`; `unknown_queued_class_names` reports such rows, and `work` and `migrate` warn about them and stop nothing (`c-coldbrew-rename`).
11. **Status is read through an API that keeps error text in the database.** `Caramel::ColdBrew.status` and `statuses` return `JobStatus` records with a state and `error_class`; the message and backtrace in `last_error` never leave the database (`c-coldbrew-status`).
12. **Hooks run after the transition is written.** `on_retry_scheduled` and `on_failed` receive `RetryScheduled` and `JobFailed` events, which are serializable to JSON. Under a worker the transition has committed and each hook runs in its own transaction; a raising hook rolls back only its own writes. Under `drain_queue!` on a spec's connection, the transition and the hook run inside the example's transaction, as savepoints (`c-coldbrew-status`).
13. **PubSub is `LISTEN`/`NOTIFY`, at most once and on commit.** `publish` runs `pg_notify` on the current Repo connection. One broker connection per process `LISTEN`s, using Caramel's transport policy without a read timeout; TCP keepalive and a periodic `SELECT 1` find a connection that stopped answering, and it reconnects with backoff and re-`LISTEN`s. Each subscriber has an ordered mailbox drained by its own fiber, so delivery never blocks the broker, and a subscription ends with the fiber that owns it (`Broker`, `c-coldbrew-pubsub`). `Caramel::SSE.relay` bridges a subscription to server-sent events with a heartbeat (`c-actions-stream`).
14. **The cache is an `UNLOGGED` table.** `Caramel::Cache` reads and writes strings in `caramel_cache` with optional TTLs (`c-coldbrew-cache`).
15. **A schedule takes a database lease per period.** `Caramel::ColdBrew.every` ticks in every process; `pg_try_advisory_xact_lock` and a `caramel_schedules` row let exactly one process run each period (`Scheduler`, `c-coldbrew-every`).
16. **The application process hosts Cold Brew, and one binary has two roles.** `serve` calls `Caramel::ColdBrew.start` unless `CARAMEL_ENV=test`, on a connection pool separate from the requests'. It starts Cold Brew inside the block that removes its socket, so invalid worker settings never leave the socket behind. `work` runs the same `start` without an HTTP server; its flags replace the worker settings, which `start` still validates, and `--no-scheduler` leaves schedules to other processes. Both refuse pending migrations and stop as [ADR 0032](0032-application-production-contract.md) decision 5 says; flags and refusals are in `c-coldbrew-run`.
17. **Specs drain queues synchronously.** No worker or poll runs under `CARAMEL_ENV=test`, and `work` refuses to start there. `drain_queue!(db, queue)` runs due jobs on the spec's connection until the queue is empty (`c-coldbrew-test`).

## Reasons

- Keeping jobs, schedules, notifications and cache in the same PostgreSQL that holds domain truth removes the dual-write problem outright. It also removes Redis and other brokers. One machine is sufficient, and state lives in the database and the hypermedia.
- Security-definer maintenance preserves Latte's least-privilege runtime roles.
- A claim that sorts the due backlog and a release that scans every partition both grow with the queue until they outlast the 5 s lock timeout; an index that matches each statement's predicate and order keeps them constant. Isolated maintenance steps keep a slow release from stopping partition creation, which is what keeps the table bounded.
- A partitioned parent refuses `CREATE INDEX CONCURRENTLY`, so the index builds take a `SHARE` lock per partition, and a linter annotation allows them.
- Waking idle fibers with the enqueue's own notification gives a one-second poll the latency of a 50 ms one without 20 claims a second per idle fiber; the poll stays because notifications are at most once.
- Per-subscriber mailboxes keep events in order under bursts. Rejected: one fiber per notification, under which a burst arrived out of order.
- A heartbeat ends a dropped client's stream at the next heartbeat instead of at the next event, and a subscription that ends with its fiber means an action that never unsubscribes does not leak.
- Maintenance runs in every process because it is idempotent.
- Reading status through a framework API keeps `caramel_jobs` free to change behind a contract, and keeps error messages, which may hold connection URLs or form values, inside the database.
- Rejected: a hook inside the failed `perform` transaction, which would be rolled back with it and could not describe the durable queue state. Calling hooks after the transition row is written is the first point where the state they describe is real.
- Running each hook in its own transaction makes its effects commit together and keeps a broken hook from affecting the worker or a spec's transaction.
- A row stores a name, not a reference, so the name must outlive the class that wrote it. Declaring the old name on the class that replaced it keeps the queue valid across a deploy without a data migration, and a compile error stops two jobs from silently sharing one.
- Reporting rather than refusing keeps `work` and `migrate` from blocking a deploy over rows that a rollback or a later alias fixes: a stranded row is already recoverable by deploying the old name back or declaring it. The report is an API, so a deploy script can fail on it.
- The worker-only process reuses `serve`'s startup and shutdown instead of a second entry point, so a deployment runs one binary in two roles. It refuses `CARAMEL_ENV=test` because specs drain queues there.
- **Released runs are counted apart from attempts.** A process can die for reasons outside the job, such as a deploy's SIGKILL or another job exhausting memory, so a released run does not spend the retry rule's attempts. A job that ends its process on every run must still stop: its third release fails it.
- A lock is released as soon as a pass finds its backend gone, or finds a backend under that PID that started after the lock was taken (a reused PID, not the locker), so the row waits a minute. Rejected: a 15-minute floor on a lock's age; `pg_stat_activity` is the ground truth a waiting period only approximated.
