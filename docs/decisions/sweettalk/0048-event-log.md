# ADR 0048: A SweetTalk context keeps its events in a log written in the command's transaction, beside rows that stay the truth

Date: 2026-10-28

Status: accepted.

## Context

An event existed only as the job rows it was carried in, pruned with their partition after seven days, and as a `pg_notify`. An audit written by a policy was eventual and retried, so an application that had to explain its numbers kept a second, hand-written audit context that could disagree with the events it followed. A projection added later started empty, with nothing to rebuild it from ([#248](https://github.com/caramelizedev/caramel/issues/248), split from [#168](https://github.com/caramelizedev/caramel/issues/168)).

A log and a rebuild then needed four more rules:

- **A busy queue.** A rebuild that refused while a job of the projection's handlers was queued or running checked once: an event that committed after the check was replayed by the rebuild and applied again by its own job, and a job running beside the rebuild could write rows the rebuild then counted. A busy application could not rebuild at all.
- **Retention.** A schedule that deleted rows let a later rebuild replay what was left without saying so.
- **Older rows.** A row logged before an event gained a required field could not be read: loading it raised on the missing key.
- **What an event led to.** An audit that asks "what did this event lead to" read each context's log by hand, joining on `cause_id` across tables ([#263](https://github.com/caramelizedev/caramel/issues/263)).

## Decision

The rules an application relies on are stated on the website ([site.html](../../../website/source/site.html)), in the sections of its Domain-Driven Design guide cited below by anchor, and in the doc comments under [src/caramel/sweet_talk](../../../src/caramel/sweet_talk). This record states what was chosen. What an event is, and how it reaches its handlers, is [ADR 0041](0041-events.md).

1. **`event_log:` on a context keeps its events in `<context>_events`, written in the command's transaction.** `context Billing, event_log: true, means: "…"` keeps them in `billing_events`. `SweetTalk.dispatch` calls each context's generated `__sweettalk_log` before it enqueues jobs; it inserts one row for every event of the context, from an aggregate's command, `create` or factory, or a service's `emit`, and for every event of a kernel the context shares, on the current connection, so the row commits and rolls back with the command. A kernel takes no `event_log:`: its events are logged by each sharer that keeps a log, under the aggregate name `<kernel>_<aggregate>` (`site#c-sweettalk-event-log`, `SweetTalk.__sweettalk_event_log`).
2. **A program without the keyword changes nothing.** `__sweettalk_log` is a no-op there: no `_events` table, no row and no extra statement in `dispatch`.
3. **The table is part of the derived schema, and it is append-only.** `Billing::Rows::Events` is a SugarORM schema, so `frappe db diff` creates it and the spec harnesses migrate it. Its `id` is a bigint identity whatever the domain's id type, and `subject_id` is nullable and takes the context's id type, uuid or bigint ([ADR 0033](0033-framework-boundary.md)). `event_id`, unique, `aggregate`, `name`, `actor`, `cause_id` and `flow_id` are text, `actor` and `cause_id` nullable, `occurred_at` is timestamptz, and `fields` is jsonb through `SugarORM::JSONB(JSON::Any)`. It has `created_at` alone, because a row is never updated. `aggregate` and `name` hold stored names, the `renamed_from:` original as the channel says it. What each column holds, the indexes and the tenant column are in `site#c-sweettalk-event-log`. A declaration whose table would be `<context>_events` does not compile.
4. **`logged` reads typed events.** `Billing.logged(Invoiced, subject: id, since: t, before: u, limit: 100)` returns `Array(Invoiced)`, each built through the event's `__sweettalk_load` from the row's fields and metadata; `subject:` takes an id or a raw id of the context's id type (`UUID` or `Int64`). `Billing.logged(subject: id)` returns every class as `Array(SweetTalk::Event)`, chosen by the row's aggregate and name. `before:` reads the log as it stood at a moment: what the program knew then, by when each event was emitted, not when what it records took effect. The order, the bounds and the errors are on `logged` and in `site#c-sweettalk-event-log` and `site#c-sweettalk-known-at`.
5. **`event_log:` says how long the log keeps an event.** `event_log: true` keeps every event. A whole number of days or weeks, as `event_log: 90.days`, keeps an event that many days: the context registers an hourly schedule with `Caramel::ColdBrew.every` ([ADR 0009](../0009-cold-brew.md)) that deletes older rows in chunks, across every tenant. Any other value does not compile, and neither does `SweetTalk.rebuild` of a projection whose context keeps its events a number of days. A log kept a number of days answers `logged` and `reached` with the rows it still holds (`site#c-sweettalk-event-log`).
6. **`SweetTalk.rebuild` replays the log through the projection's own handlers.** In one transaction it takes `pg_advisory_xact_lock(LOCK_NAMESPACE, hashtext(table))` in Cold Brew's two-key namespace, deletes the projection's rows, pages the log by `id` and runs each followed event through the generated `__sweettalk_on_*`, one unit of work per event and one per element with `each:`. It enqueues nothing, so a follower that says `after:` the projection is not released. The macro refuses a projection whose context keeps no log, or that follows an event the log does not keep. A handler that reads present state replays against present state, and a rebuild covers only the events logged since the keyword was set (`SweetTalk.rebuild`, `site#c-sweettalk-event-log`).
7. **A rebuild leaves an event to the job that still has to apply it.** For each page it reads the jobs of the projection's handlers, and of the handlers each says `after:`, that carry one of the page's events and are neither finished nor failed, under every name `renamed_from:` gives them. It does not replay an event such a job carries, nor an element of `each:` whose job is among them: that job applies it once the rebuild commits. It replays an event whose job finished, failed or was pruned with its partition. Every job of a projection's handler takes `pg_advisory_xact_lock_shared` on the same key before its handler runs, so none runs while its projection rebuilds, and a rebuild waits for those that run. A log row commits with its jobs, a predecessor's finish with its followers' enqueue, and no handler job of the projection finishes during the rebuild, so each event is applied once. A failed job that an operator retries after the rebuild applies its event a second time, since the rebuild replayed it: discard it instead (`SweetTalk.__sweettalk_rebuilding`, `site#c-sweettalk-event-log`).
8. **`rebuild` says what it did.** It returns a `SweetTalk::Rebuilt` with `replayed`, `deferred` and `oldest`; a log turned on after a context's first events holds none of them, and `oldest` says where it starts (`SweetTalk::Rebuilt`).
9. **`reached` walks the logs forward by cause.** `Books.reached(event)` returns a `SweetTalk::Reached`: every event that followed from *event*, across every context that keeps a log, and the same events grouped by subject. Every event emitted while a handler, a compensation, a deadline or a process step runs carries that event's id as its cause; a command, a service or a unit called outside a handler starts a chain. The walk passes only through logged events, so an event of a context without a log, or one a retention window pruned, ends its chain. The order, the grouping key and the errors are on `SweetTalk::Reached`, `SweetTalk.__sweettalk_reached`, a log's `__sweettalk_caused` and in `site#c-sweettalk-event-log`.
10. **The log is proved against PostgreSQL.** `spec/sweet_talk/event_log_spec.cr`, on the billing desk, and the tenant shop's examples prove the rows, the reader and its bounds, the scheduled prune, the rebuild and its lock, that a queued job's event is left to it and applied once, that a follower's waiting predecessor defers the event, that a failed job's event is replayed, and that a projection's job waits for the rebuild lock; `spec/sweet_talk_tenancy` proves an element of `each:` left to its job. The fixtures `rebuild_without_log`, `rebuild_with_retention`, `event_log_span` and `event_log_table_taken` prove the refusals.

## Reasons

- **In the command's transaction, or not at all.** A log written by a policy would be eventual and could disagree with the rows; one row inserted beside the job rows costs one statement and cannot be lost or sent for a rolled-back change.
- **Rows stay the truth.** The log serves audits, rebuilds and reads of what happened; no aggregate is loaded from it, so a context that never turns it on is untouched, and one that does keeps the model in which state lives in rows.
- **A kernel's events go to every sharer that logs.** A kernel's command may run from any sharer, or from an action; the log is the sharer's, kept so the sharer's projections can be rebuilt, and a projection following a kernel event needs every such event in its own context's log, whoever ran the command. The aggregate column leads with the kernel's name so a kernel's `Voucher` and the context's own cannot collide.
- **Stored names, not class names.** `aggregate` and `name` are what the channel stores, so `renamed_from:` keeps old rows readable as the job names and tables already are.
- A queued handler job would write once more what the replay wrote, so a rebuild leaves that job's event to it; the advisory lock keeps two rebuilds apart.
- **The queue already knows what is left to apply.** Commanded's Ecto projections keep a `last_seen_event_number` beside the read model, and Marten a high-water mark that waits for gaps in the sequence; both need a cursor per projection, written with every event. A queued SweetTalk job already names the event it will apply, and the log row commits with it, so asking the queue for each page is exact without a new table. The shared lock costs one statement per projection job.
- **Applying an event twice is the failure every lineage framework names.** Spatie's replay with `--from` warns that it "does not track which events have already been processed".
- **Rejected: refusing a rebuild while a handler job is queued.** It traded the double application for a rebuild nobody could run on a busy application, and its check ran once, so an event that committed after it was still applied twice.
- **Rejected: a watermark.** Every job would carry its log id, and the replay would skip up to one.
- **Rejected: a cursor table per projection.** A write on every event and a second truth beside the queue.
- **A rebuild runs only projections.** Spatie never calls reactors on replay and Axon's `@DisallowReplay` keeps side effects out; a rebuild enqueues nothing, so policies and processes act on the world once.
- **Retention is a property of the context, so the compiler knows when a rebuild cannot be complete.** Carbonite purges only what every outbox has passed, and EventStore refuses deletes unless a setting allows them; here the declaration is the setting. A horizon recorded at run time would find out late what the declaration already says. Days and weeks, as literals, because a log is kept for audits measured in days and a literal can be checked.
- **Rejected: refusing at run time after a prune, from a recorded horizon.** It finds out at run time what the declaration says at compile time.
- A default per field is the smallest thing that keeps old rows readable; `older:` and its reasons are in [ADR 0041](0041-events.md).
- **Rejected: a CHECK on the log's fields.** It would stop an old binary's rows during a deploy and says nothing about queued jobs.
- **One lock key per table.** A rebuild in one tenant holds that projection's jobs in every tenant back while it runs. A rebuild is rare and short, and one key keeps the lock the same with and without tenancy.
- **What was known at a time is a read of the log.** `occurred_at` is stamped when an event is emitted, so the rows before a moment are what the program knew then. `before:` excludes its bound and `since:` includes it, so two reads split at one moment share no event and miss none. A log kept a number of days answers with what remains, as `since:` and `reached` do; its declaration already says how far back it reaches.
- **What is in effect after a correction is a column.** A command that finalises a correction sets the aggregate's effective result, so a reader asks the row and the log says when it changed. Astrona scanned its finalised corrections newest first for it, in 19 lines with three callers and a second copy.
- The log already holds the cause of every event, written in the transaction that made it; the walk of `reached` is the join an application wrote by hand, once.
- **Rejected: following the aggregate's `flow_id`.** A flow groups everything one command started, including unrelated events; the cause says which led to which.
- **Rejected: `SweetTalk.after_dispatch { }`**, the in-transaction hook [#248](https://github.com/caramelizedev/caramel/issues/248) named as the fallback. It gives an application a place to write its own log, but every application would write a different one and nothing could rebuild from it.
- **Rejected: event sourcing.** Loading an aggregate from its log changes every command's read and the model in which rows are the truth; the log is kept beside the rows, not instead of them.
- **Rejected: keeping one aggregate's events as its truth, for the present.** With `kept: :as_events` only a fold of its events would write the row, and `find(id, as_of: t)` would fold to a moment. Commands would still read the row, so the reason against event sourcing does not reach it. On Astrona's corrections, 2,306 lines, a reading of the code finds about 55 lines it would delete and none of the seven documented refusals it would lift: the rest is a replay of what would have been recorded under revised inputs, and policy, which no fold of recorded events computes. Ten percent, 230 lines, or one lifted refusal would have justified the word, so it waits for a second application that shows the need. Rows versioned by a `daterange` key `WITHOUT OVERLAPS` (PostgreSQL 18) break one row per id and its lock; a `<table>_history` beside each table adds a table and says nothing about corrections.
- **Rejected: logging only what a projection follows.** The audit needs every event, and a projection added later follows events nobody followed when they occurred.
