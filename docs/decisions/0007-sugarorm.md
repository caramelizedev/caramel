# ADR 0007: SugarORM maps each table to an immutable schema, writes through class changesets, tracks preloads in types and keys records by a UUIDv7 the application mints

Date: 2026-09-27

Status: accepted.

## Context

An application needs pure schemas, compile-time association safety, explicit changesets, a fluent facade and typed SQL. Crystal cannot express some natural shapes directly:

- a changeset struct inheriting from a generic type;
- `preload(:users)` with a return type that depends on a symbol's value;
- a `NotLoaded` error that appears at build time and needs somewhere to live.

Two further problems needed a rule:

- **Calendar days.** Crystal has no date type without a clock, and a `Time` field is a `timestamptz`, which carries a time of day and a zone a calendar day does not have. A due date or a birthday kept as validated text needs a regular expression `CHECK` and a string in the model, and takes no range query.
- **Identity.** A record keyed by an identity column has no id until its row is written. An application cannot name it before the insert: not in an event built beside it, not in a job queued in the same step, not in a URL handed out first. Sequential ids also tell anyone who sees one how many records exist.

## Decision

The rules an application relies on are stated on the website ([site.html](../../website/source/site.html)), chiefly its SugarORM reference, in the sections cited below by anchor, and in the doc comments under [src/sugar_orm](../../src/sugar_orm). This record states what was chosen. Typed conflict errors, retries, aggregates, joins and reads by primary key are in [ADR 0052](0052-sugarorm-conflicts-and-reads.md); deriving migrations from the schema is in [ADR 0008](0008-migrations.md).

1. **A schema is an immutable struct that declares its table once.** A model is `struct Team < SugarORM::Schema` with one `schema "teams" do … end` block, and `scope name(args) { … }` defines sentence scopes. Instances have getters only, plus `with(**)` for a changed copy. They hold no connection and have no callbacks, and every instance is a stored row. Each table belongs to one schema: a second concrete schema that names the same table fails to compile, naming both. The declarations (`field`, `timestamps`, `belongs_to`, `has_many`, `has_one`, `index`, `drop_column`, `check`, `json`), their options and what fails compilation are in `site#c-sugarorm-schemas`.
2. **A record is keyed by a UUID the application mints, or by an Int64 the database assigns.** `field id : UUID, primary: true` is a `uuid NOT NULL DEFAULT uuidv7() PRIMARY KEY` column, so PostgreSQL 18 is the floor for UUID-keyed tables; `field id : Int64, primary: true` is a bigint identity column. Any other primary key fails compilation (`site#c-sugarorm-schemas`). Caramel checks no server version: PostgreSQL before 18 fails the `CREATE TABLE` with its own error. Each schema declares `PrimaryKey` and `SUGAR_KEY`; `find`, `find!` and `page(after:)` take `PrimaryKey`, `each_batch` reads in its order, and `SugarORM::Page` carries the key type. `UUID` and `UUID?` are ordinary field types too: rangeable in `where`, with no default. `caramel_jobs` and `caramel_migrations` keep a bigint key. `frappe make resource` writes a UUID key, and `--int64` an Int64 key (`site#c-commands-frappe`). A tenant's key is stated by [ADR 0025](0025-tenancy.md), how a `UUID` binds in contracts and routes by [ADR 0003](0003-routing-and-ingress.md), and SweetTalk's ids by [ADR 0033](sweettalk/0033-framework-boundary.md).
3. **The insert changeset mints the id.** An insert changeset of a UUID-keyed schema takes its id from `SugarORM.uuid7` when it is built; `changeset.id` returns it and `changes` lists it (`Changeset#id`). `SugarORM.uuid7` implements RFC 9562 method 3: a 48-bit millisecond time, 12 bits of sub-millisecond time and 62 random bits, each id greater than the last this process minted. An Int64-keyed changeset's `id` raises `SugarORM::Error` before the insert. A raw `INSERT` that names no id gets `uuidv7()`.
4. **`param id` is the only way a client supplies an id.** A changeset that declares `param id : UUID` takes a client's id, and only a UUID key allows it. `DefaultChangeset` and the facade never take an id. The refusals and the two field errors are in `site#c-sugarorm-schemas`; the second, on an update that changes the id, is the framework message `errors.key_kept` ([ADR 0024](0024-internationalization.md)).
5. **A foreign key follows its target's key type.** A `belongs_to` column is `uuid` or `bigint` after its target's key, and a `tenant` column does the same ([ADR 0025](0025-tenancy.md)). The target may be declared later in the program; a `param` for a `belongs_to` column is checked once the program is complete. `on_delete:` and its refusals are in `site#c-sugarorm-schemas`.
6. **Every other type is stored through a codec, as text.** A field's type is `String`, `Int32`, `Int64`, `UUID`, `Bool`, `Float64` or `Time`, optionally nilable, or any type with `codec: C`. Rows read a codec column as text and writes bind the encoded text. The contract, the column types a codec may name, the refusals and `SugarORM::JSONB(T)` are in `Codec` and `site#c-sugarorm-codecs`. A codec declares `ORDERABLE = true` when its column orders the way its values do, and keyword `where` then takes a closed, beginless or endless `Range` of the field's type; `order_by` takes every field and never needs the constant.
7. **A decimal codec exists, behind a require of its own.** `SugarORM::DecimalCodec(P, S)`, in `sugar_orm/decimal`, stores a `BigDecimal` in a `numeric(P,S)` column, and its `encode` refuses with `ArgumentError` a value PostgreSQL would round or overflow. `sugar_orm` does not require that file, so a program that stores no `BigDecimal` links no GMP. Its text and its refusal are in `DecimalCodec`, `Decimal.plain` and `Decimal.fits`.
8. **A calendar day is a `SugarORM::Date` in a `date` column.** `SugarORM::Date` is a struct with `year`, `month` and `day`, comparable and hashable, with no time of day and no zone; it names its weekday. `SugarORM::DateCodec` stores it and declares `ORDERABLE`. The column type makes PostgreSQL refuse a day that does not exist. Its range, text and conversions are in `Date` and `site#c-sugarorm-codecs`; `DateCodec.decode` refuses `infinity`, `-infinity`, a BC date and any text that is not `YYYY-MM-DD`. `format_type` spells the type `date`, with no modifier, so the declared and the live type compare equal as strings, and the DDL, the introspection and the differ create and compare the column with no other change. An application's own calendar type writes its own codec with `sql_type` `date`.
9. **A text column declared `date` is retyped behind a check; every other type change halts.** When a field is declared `date` and the live column is `text`, the differ derives the change instead of halting, with or without `--dev-override`. The transactional migration first locks the table and counts the rows whose text is not a calendar day written `YYYY-MM-DD`, and raises when there are any, so it rolls back and changes nothing. It then drops the column's default, when it has one, and runs `ALTER TABLE … ALTER COLUMN … TYPE date USING "col"::date`. What passes the check and what the error shows are in `site#c-sugarorm-migrations` and `DDL.render`. `date` to `text` halts, and `--dev-override` alters it in development only.
10. **Constraints are declared in the schema and named by SugarORM.** `check stock: 0.., quantity: 1..10` bounds integer fields, and `check :dates, "starts_at < ends_at"` adds a named SQL expression. Each becomes the CHECK constraint `check_<table>_<name>`, where a range check's name is its column. Range checks are compared by their bounds and expression checks by name only, so changing an expression needs a new name. An index is named `index_<table>_on_<columns>`, and SugarORM shortens a name over 63 bytes to `index_<table>_on_<cut>_<fnv8>` (`Catalog.index_name`); a check name over 63 bytes fails compilation. A tenanted schema's unique index also holds the tenant column ([ADR 0025](0025-tenancy.md)). How `frappe db diff` adds an index or a check to an existing table, and what rows that break a new check do to `frappe migrate`, is in `site#c-sugarorm-migrations`.
11. **A version field refuses a stale update.** `field lock_version : Int32, version: true` versions the record: every changeset update adds `AND "lock_version" = $n` and increments it, and a mismatch writes nothing. A changeset given `lock_version:` checks that version instead of the loaded one. Deletes do not check it. The field's rules and the error are in `site#c-sugarorm-saving`.
12. **A record's JSON holds only the columns its `json` line lists.** A schema without a `json` line fails compilation where a record would be written as JSON (`site#c-sugarorm-schemas`). `frappe make resource` lists the id, its fields and the timestamps, never the tenant column.
13. **A changeset is a class.** Changesets are `abstract class SugarORM::Changeset(T)` subclasses that declare `param` fields, checked against the schema at compile time, and write `validate(cs)` as a method taking the changeset. A changeset accumulates errors and outcome: it is the mutable boundary, and schemas stay pure values. `SugarORM::Repo.insert` and `SugarORM::Repo.update` return the same changeset, reporting `saved?`, `record` and `errors`. The validators, `unique_constraint`, `check_constraint` and what the default changeset maps are in `site#c-sugarorm-changesets`.
14. **An upsert is declared on the changeset and targets a declared unique index.** `upsert on: :tea_id, update: [:sold]` makes the insert `INSERT … ON CONFLICT` on that index. With no `update:` fields it is `DO NOTHING`, and a second read returns the existing row. The target, the key and the update fields are checked at compile time (`upsert`, `site#c-sugarorm-saving`).
15. **The facade builds a changeset and returns it.** `Team.create(**)` and `team.update(**)` build `Team::CreateChangeset` or `UpdateChangeset` when the program defines them, and otherwise a generated `Team::DefaultChangeset`. Both run through the Repo and return the changeset; the bang forms return the record or raise `SugarORM::Invalid`. Every facade method and query terminal also accepts an explicit `db` handle first (`User.create!(db, …)`, `.first!(db)`), as `site#c-sugarorm-saving` and `site#c-sugarorm-queries` list.
16. **An association that was not preloaded has no methods.** On a plain record an association accessor returns a generated sentinel, `Team::UsersNotLoaded(Remediation)`, so any use fails to compile at the caller's line, and the type name carries the remedy (`NotLoaded`, `site#c-sugarorm-preload`). `preload(:users)` resolves through an overload per association whose parameter is a one-member enum; Crystal autocasts the symbol, so an unknown association is a compile error that lists the valid ones. Each overload merges a loader into the query's type parameter, and preloading terminals then return `SugarORM::Loaded(Team, NamedTuple(users: Array(User)))`, where `users` is a real array.
17. **A preload costs exactly one extra query per association.** A `has_one` reads one row per owner, the one with the lowest primary key, with `SELECT DISTINCT ON (fk) … ORDER BY fk, pk` (`HasOne`). A `has_many` is not bounded.
18. **Queries are immutable and check names and types.** `where` keywords are generated per schema and typed: a value, an `Array`, a `Range`, or the literal `nil` for IS NULL. A value that may be nil does not compile: `where` returns `T::<Column>MayBeNil`, which has no query methods. `order_by` validates the field through a generated `Field` enum. `where_condition` adds a `SugarORM::Condition` built elsewhere and is a method of its own, not an overload of `where`. Each schema generates an encoder per column, so a caller that builds a `Condition` binds the same text a typed `where` binds. The clauses, `where_null`, raw fragments and their refusals are in `site#c-sugarorm-queries`.
19. **`lock` is `FOR UPDATE` on the rows a query returns.** It keeps the tenant scope and runs only inside a transaction, and `count`, `exists?` and `delete_all` refuse it. Applications lock several rows in one order (`order_by(:id).lock`) and still check permissions (`site#c-sugarorm-queries`).
20. **The Repo holds one pool and binds connections to fibers.** One application pool is set at boot. `Repo.bind` binds a connection or transaction to the current fiber, which Corretto and Cold Brew use, and `transaction` nests as savepoints (`Repo.bind`, `Repo.transaction`).
21. **Hand-written SQL is read as named tuples.** `SugarORM.sql(query, *args, as: {team_id: Int64, total: Int64})` returns `Array(NamedTuple)` for CTEs, window functions and `RETURNING`, and raises `SugarORM::ShapeError` when the result's column names and order differ from the declared keys (`site#c-sugarorm-sql`).

## Reasons

- Macro-generated overloads, enums and type-carrying sentinels put every contract in the type system, so misuse fails at compile time and at the caller's line. Crystal's `{% raise %}` and `method_missing` report errors at the outermost top-level expression instead.
- Changesets as classes keep the `def validate(cs)` cadence while leaving schemas purely immutable.
- Explicit handle overloads and fiber binding let tests and jobs share one transaction without global state leaking between fibers.
- Failed validation performs no write, and constraint violations stay explicit.
- Remediation travels with the error, in the sentinel's type name.
- Codecs keep exact decimals and structured values out of the type map, so an application that never uses `BigDecimal` never links GMP, and each application picks its own decimal type. GMP is a link-time dependency, so `SugarORM::DecimalCodec` arrives by one opt-in require; one require is cheaper than a flag.
- Reading a codec column as text and binding the encoded text means no value passes through a float. `BigDecimal#to_s` prints an exponent past some size, so the decimal codec writes its own plain digits.
- `numeric(20,8)` rounds a ninth decimal silently and raises on a thirteenth digit. A value that cannot be stored exactly is a mistake in the caller's data, and the codec says so before PostgreSQL does.
- Jason refuses to encode a struct that derived no encoder, and warns that encoding all fields leaks the ones added later. Rails and Laravel serialise every attribute by default, so a column such as `password_digest` reaches a client unless someone remembers to hide it. A `json` line makes each exposed column a decision, and a missing one a compile error.
- A lookup such as `where(reset_token: token)` must not match the rows whose token is NULL when `token` happens to be nil. Ecto refuses a comparison with nil for the same reason; here the compiler knows whether a value can be nil, so the refusal is a compile error. The literal `nil` stays, because it cannot be nil by accident. The refusal shipped without a deprecation release: a compile-time warning is reported in the framework's file, and Crystal hides warnings from `lib/`.
- `where_condition` is its own method because another `where` overload turns "no parameter named" into "no overload matches".
- PostgreSQL rewrites the SQL of an expression check, so the differ can compare one only by its name.
- The schema macro and `Catalog.index_name` build one index name at compile time and at run time, so the differ, the unique-violation mapping and the catalog agree.
- A changeset given `lock_version:` lets a form carry the version it was rendered from.
- `DISTINCT ON` returns the one row per owner in the statement itself; a `has_one` that loaded every child held them all in memory to keep one.
- **A struct, not `Time`.** A `Time` carries a zone, so a day read in one zone and written in another moves by one. A `Date` has no zone to disagree about.
- **A constant, not a method.** `where` is checked at compile time, and a macro can read a constant's value but cannot call a method. A codec opts in by writing the constant, which is why the codec must be defined before the schema that names it.
- **Opt-in ranges.** A numeric codec's values are text in Crystal and numbers in SQL, and `text` compares by the database's collation, so a range there would answer by rules the application did not choose. A `date` compares the same way in both. Binding the encoded `YYYY-MM-DD` text lets PostgreSQL read it as a `date`, so the comparison is by day.
- **Strict text.** A date that prints as `24.10.2026`, `infinity` or `0044-03-15 BC` has no `Date`, so `decode` says so and names `DateStyle` instead of guessing a day; PostgreSQL's `DateStyle` `SQL`, `Postgres` or `German` prints such text through `"col"::text`, and the `ISO` styles always print `YYYY-MM-DD`. On the way in, `'10/11/2026'` casts to a different day under each `DateStyle`, `'today'` is a different day on each run and `'infinity'` has no `Date`. Requiring `YYYY-MM-DD` and `pg_input_is_valid` (PostgreSQL 16 and later; the block raises a clear error on an older server) reports each of them as a row instead of changing it.
- **The check in the migration.** `frappe db diff` sees only a scratch branch of the development database, not the rows a deploy will meet, so each environment checks its own rows. Locking first means no row arrives between the check and the rewrite.
- Rejected: a `Time` field with a date codec, which hides the zone.
- Rejected: deriving text to date with no check, which stops at the first bad value and does not count the rest.
- Rejected: halting every text to date change, which sends every application through add, backfill and drop for a change the check makes safe.
- An id the application holds before the insert lets one step name a record in events, jobs, URLs and child rows without a round trip.
- UUIDv7 leads with time, so new keys land at the right of a B-tree index as a sequence's do, and ordering by id stays roughly creation order. A random UUIDv4 scatters inserts across the index.
- **Rejected: the stdlib `UUID.v7`.** It has no counter, so two ids in one millisecond order at random; the sub-millisecond bits and the per-process floor keep a process's ids strictly increasing, even when the clock stalls or steps back.
- **Rejected: the database alone mints the id.** The application would again wait for `RETURNING` to learn the key. `uuidv7()` stays as the column default so raw SQL and other writers still get a v7 key.
- **Rejected: a version check for PostgreSQL 18.** On an older server the first migration that creates a UUID-keyed table already fails with `function uuidv7() does not exist`; a check would add a query at every start to report the same thing.
- **Rejected: taking an id from any changeset.** An id a form could set lets a client pick or overwrite keys; one declared `param id` makes the choice visible and reviewable.
- **Bigint stays where order or a counter is the point.** Jobs and migrations are framework bookkeeping no application id refers to.
