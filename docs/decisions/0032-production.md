# ADR 0032: An application ships as one static Linux binary that states what a deploy tool can rely on and hardens every response itself

Date: 2026-10-10

Status: accepted.

## Context

An application has to run on a Linux server it was not built on: read `public/` from where it is unpacked, run Cold Brew's workers apart from the web process, and finish the requests in flight when it is told to stop. Servers, proxies and hosting providers change on their own schedule, and deploy tools sit outside the framework, so the binary states what they can rely on.

The same binary is the last thing between the proxy and the browser. An application that needs a payment provider's script, an embedded player or an inline script with a nonce must be able to say so without putting another handler in front of Caramel, and a browser that once reached the site over HTTP keeps trying HTTP unless something sends `Strict-Transport-Security`. Static files need rules too: ACME challenges, `security.txt` and app-link files live under `public/.well-known/` while other hidden files must stay unservable, a route such as `/.well-known/change-password` must be reachable, and a file must not be read whole into memory, go without validators, or answer 500 without the security headers when it is deleted between its lookup and its read.

## Decision

The rules a deploy tool and an application rely on are stated on the website ([site.html](../../website/source/site.html)), chiefly its production guide and its security reference, in the sections cited below by anchor, and in the doc comments under [src/caramel](../../src/caramel) and in [src/frappe/release_build.cr](../../src/frappe/release_build.cr). This record states what was chosen: first the production contract, then the headers of every response, then static files.

1. **The framework ships an artifact and a runtime contract, not a deploy tool.** It ships the release artifact and the runtime behaviour below. It ships no command that provisions servers or deploys; a deploy tool works from this contract (`site#c-deploy-gaps`).
2. **`frappe build` compiles a static `linux/amd64` binary in a digest-pinned container.** It compiles the `shard.yml` target of the committed tree with `crystal build --release --static` in `crystallang/crystal:1.22.1-alpine@sha256:9beda8a9d4a3659c29d185cc18f3fb9b382421bb6a4a59b8f266a6fb4ccc9f16`, or in the digest-pinned image `CARAMEL_BUILD_IMAGE` names, after installing Alpine's `gmp-static`. It keeps debug info and passes neither `-D caramel_development` nor `-Dpreview_mt`. It prints the artifact's absolute path as its only line on standard output; progress goes to standard error. A container engine is needed only for this build: principle 3 of CONTRIBUTING.md (no containers in development) governs development, not release builds. The refusals (a dirty tree, tracked changes left by publishing `app/assets` into `public/`, an image named without a digest) are in `site#c-deploy-contract` and `ReleaseBuild`.
3. **The artifact is one tarball of `bin/<shard>` and `public/`, with a checksum and a bill of materials beside it.** Its name carries the UTC build time and the commit's sha. It holds nothing else: no source tree and no Node or other external runtime. A file the binary reads at run time must be embedded when it compiles (`read_file`) or be a browser-fetched asset in `public/` (`site#c-deploy-files`). The name's pattern, the `.sha256` file and what the CycloneDX 1.5 `.sbom.json` lists are in `site#c-deploy-contract`, `ReleaseBuild.checksum` and `ReleaseBuild.sbom`.
4. **`serve` finds `public/` through `CARAMEL_ROOT`.** It reads `public/` from `CARAMEL_ROOT` when that is set, and from the compile-time root otherwise (`site#c-deploy-public`, `CommandLine.served_root`).
5. **Web and workers are two roles of one binary, run as separate processes.** A production deployment runs its web processes with `serve --no-workers` and one `work` process. `serve --no-workers` starts no Cold Brew workers and no scheduler, but keeps the PubSub broker and maintenance; `serve` without the flag hosts all of Cold Brew, as [ADR 0009](0009-cold-brew.md) records (`site#c-deploy-now`, `site#c-coldbrew-run`).
6. **Shutdown drains what is in flight under one deadline.** At the first SIGTERM or SIGINT, `serve` closes its listener, stops claiming jobs and starting schedule blocks, and ends every PubSub subscription, so a stream that waits on one ends. Requests, jobs and schedule blocks in flight run on; the process exits 0 when they finish or when `CARAMEL_SHUTDOWN_TIMEOUT` seconds have passed, and a second signal exits 1 at once. `work` stops the same way. A supervisor allows `CARAMEL_SHUTDOWN_TIMEOUT` plus 5 s before it kills a process, and a deploy moves the proxy before it stops a process. The variable's range and default, what a cut-off job and a late request on a kept-alive connection get, and every other outcome are in `site#c-deploy-shutdown`, `site#c-deploy-env`, `CommandLine.shutdown_timeout` and `Broker#end_subscriptions`.
7. **A process is ready when its own socket answers `GET /health`.** A new process is ready when its own socket answers `GET /health`, with `Host` set to the authority of `APP_ORIGIN`, with 200 and body `ok`; the generated route touches no database. A deploy sends traffic to a process only after that. Two processes cannot share one socket path, and `serve` refuses an occupied one, so each new process binds its own path and the proxy moves to it, as `frappe dev` does (`site#c-deploy-ready`).
8. **`APP jobs unknown` checks the queue against a binary.** It prints `unknown_queued_class_names`, one per line, and exits 1 when any exist. With no `caramel_jobs` table yet, it prints nothing and exits 0 (`site#c-deploy-unknown`, `JobsCommand.unknown`).
9. **The database is reached over a verified session by two least-privileged roles.** Connections use TCP with `sslmode=verify-full` (plus `sslrootcert` for a private CA), or a Unix socket in a directory owned by the application's user. They are direct or session-mode, never transaction-pooled. One database is owned by a migration role; a runtime role gets DML through default privileges; the application needs no superuser and no extensions. `APP db roles DATABASE MIGRATION_ROLE RUNTIME_ROLE` prints the psql script that creates them, built from the same code that gives Latte's sites their grants. It refuses a name that does not match `[a-z_][a-z0-9_]*`, and limits the runtime role to 24 connections, which must cover every process, old and new, during a deploy. What the script grants, why a non-superuser can run it and when it stops are in `site#c-deploy-database` and `DatabaseRoles`.
10. **PostgreSQL enforces the timeouts, and the environment sets them.** Each pooled connection sets `statement_timeout` and `lock_timeout` when it opens, from `CARAMEL_STATEMENT_TIMEOUT` and `CARAMEL_LOCK_TIMEOUT`, or for `migrate` from `CARAMEL_MIGRATION_STATEMENT_TIMEOUT` and `CARAMEL_MIGRATION_LOCK_TIMEOUT`; by default `migrate` has a lock timeout and no statement timeout. A connection's reads time out 5 s after its statement timeout; with no statement timeout the client waits, and TCP keepalive finds a lost server. `migrate` retries a migration that hits its lock timeout after 1, 2 and 4 s, and runs online migrations without one, as the lock-retry rule of [ADR 0008](0008-migrations.md) says. Ranges and defaults are in `site#c-cremaref-env`, `Database::Limits` and the constants of `Database`.
11. **The environment sizes the pool, and a process has a fixed connection budget.** A command's pool holds at most `CARAMEL_POOL_SIZE` connections, and a checkout from it or from Cold Brew's pool waits `CARAMEL_POOL_TIMEOUT` seconds, then fails (`site#c-cremaref-env`, `Database::PoolSettings`). A `serve` or `work` process holds at most `CARAMEL_POOL_SIZE` + queues × `CARAMEL_WORKER_CONCURRENCY` + 5 connections as the runtime role: its own pool, Cold Brew's pool with its four spares (`ColdBrew::SPARE_CONNECTIONS`: maintenance, two schedule blocks, and one for the recorder and console), and the LISTEN connection.
12. **A deploy cuts over in a fixed order, and migrations never roll back.** The new binary runs `migrate` while the old one serves; the migration lint rules of [ADR 0008](0008-migrations.md) refuse a migration that locks an existing table against its writes, destroys or rewrites its rows, or hides such a statement in a `DO` block, unless the author annotates it, and compatibility with the serving binary is the author's job. The new binary's `jobs unknown` passes before cutover. The old binary's workers stop before the new binary takes traffic. `serve`, `work` and `seed` warn and start when the journal holds migrations the binary lacks, so an old process restarted after the new binary's `migrate` keeps serving until cutover; a migration the journal lacks still refuses, and `migrate` and `lint` still refuse a journal ahead of them. Going back across a migration means restoring the database. The messages are in `site#c-deploy-order`; `Migrator#pending` states the journal rule.
13. **`serve` listens on a Unix socket that its user alone, or one named group, can reach.** `serve` binds `CARAMEL_SOCKET` with mode 0600 in a directory only its user can reach. With `CARAMEL_SOCKET_GROUP=GROUP` the directory may instead belong to the user and GROUP, with no group write and nothing for others. The socket then gets group GROUP and mode 0660, so a proxy running as another user in GROUP can connect. The ops socket always needs a private directory, which `CARAMEL_OPS_SOCKET` places it in (`site#c-deploy-env`, `Crema.private_directory?`, `Crema.group_directory?`, `site#c-cremaref-ops`).
14. **Every response carries three security headers, and `serve` adds HSTS in production.** The three are `X-Content-Type-Options`, `Referrer-Policy` and a `Content-Security-Policy` whose default allows the application's own origin only; their values are in `site#c-security-headers` and `ContentSecurityPolicy.default`. `serve` sends `Strict-Transport-Security: max-age=31536000` on every response when `CARAMEL_ENV` is production or unset, and never in development or test; a proxy need not add it. There is no `includeSubDomains` and no `preload`, and no setting for either (`Application::STRICT_TRANSPORT_SECURITY`).
15. **The policy is a value the application changes once and an action changes for one response.** `Caramel::ContentSecurityPolicy` holds each directive with its sources, in order. `Caramel.content_security_policy` is the policy every response carries; an application changes it in `config/application.cr`, before the application is built, and `Application` copies it when it is built. `content_security_policy` in an action returns a copy that only this response carries, and a header an action sets itself is kept as it is. A policy changes through `add`, `set` and `delete`; a `-src` directive that `add` creates, other than `default-src`, starts from the sources of `default-src`, and a name or source that fails validation raises `ArgumentError`. What each method does is in `site#c-security-headers` and the doc comments of `ContentSecurityPolicy`.
16. **A nonce belongs to one response and exists only when an action asks.** `csp_nonce` in an action returns a random nonce for this response and adds it to the response's `script-src` and `style-src`. It covers only the response that carries it, not a fragment htmx swaps into a page loaded earlier, which the page's policy governs (`site#c-security-headers`, `Action#csp_nonce`).
17. **A request is checked against the host, then `public/`, then the router, and no path leaves `public/`.** A path that could leave the directory is refused, and a file whose real path lies outside `public/` answers 404. A path with a hidden segment is never served from `public/`, except when its first segment is exactly `.well-known`; every other such path, and a `.well-known` path that no file answers, goes to the router, so a route may serve `/.well-known/change-password`. The refused paths and their statuses are in `site#c-security-static`.
18. **A file is streamed, validated and cached by its name.** GET and HEAD serve a file; any other method on an existing file answers 405. A GET streams the file with its `Content-Length`, and HEAD answers the headers alone. Range requests are not supported and `Accept-Ranges` is not sent. Every file answer carries `Last-Modified` and `ETag`, a strong tag of the file's size and modification time; `If-None-Match` decides when it is present (weak prefix and `*` allowed), otherwise `If-Modified-Since` does, a date that does not parse is ignored, and a 304 carries the validators and `Cache-Control` only. `Cache-Control` is `immutable` for a year for a name that ends in a three-part version and an extension, and `no-cache` for every other name (`site#c-security-static`, `Application::VERSIONED_ASSET`, `Application#not_modified?`).
19. **A file that vanishes is the router's, any other read failure is a reported 500, and static files stay untraced.** A file that vanishes between the lookup and the open goes to the router. Any other read error is reported to Crema with source `static` and answers 500 with the security headers; its body and `Cache-Control` are in `site#c-security-static`. Static files stay untraced ([ADR 0027](0027-crema.md), `site#c-cremaref-ids`).

## Reasons

- **Deployment is a separate product.** This contract is all a deploy tool needs from the binary. Rejected: a deploy command in Frappé.
- **Building off the server.** A PHP build is an install and a bundle, so a tool such as Forge runs it on the server. A Crystal release compile is too heavy for a small server, so the build runs where the developer works, as Vapor does. The pinned image keeps the build reproducible, as [ADR 0001](0001-toolchain-and-setup.md) pins the development toolchain; overriding it, say for a patched OpenSSL, trades that for the operator's own digest, which the SBOM records.
- **A static musl binary.** One file, with no shared libraries to install on the server.
- **`gmp-static` at build time.** The image has GMP's shared library but not its archive, and a static binary that uses `BigDecimal` needs the archive. Alpine's repository for the image's release supplies it, so its revision can change between builds of one Caramel release; the SBOM records it.
- **Debug info kept.** Crema reports carry backtraces ([ADR 0027](0027-crema.md)). Rejected: `--no-debug`.
- **`preview_mt` left out.** It is untested in Caramel. Rejected: `-Dpreview_mt`.
- **`CARAMEL_ROOT`.** It is the smallest change that lets a binary leave its build path.
- **Separate workers.** Long jobs drain without holding the web process.
- **Workers stop before cutover.** A row whose class the running binary lacks fails without retry (stored class names, [ADR 0009](0009-cold-brew.md)).
- **One shutdown deadline.** A job that never ends would hold a deploy for ever, and a supervisor needs a bound it can wait for. Ending PubSub subscriptions at the first signal stops an open SSE stream from using up the drain. A second signal is the operator's word that the wait is over.
- Rejected: `SO_REUSEPORT` handover on one socket path.
- Rejected: restore points and migration rollback.
- **Transaction-mode poolers ruled out.** LISTEN, `migrate`'s session advisory lock and `locked_by = pg_backend_pid()` need a session.
- **`CARAMEL_SOCKET_GROUP`.** A proxy that terminates TLS holds keys the application must not read, and vice versa. A group that may enter one directory and connect to one socket grants nothing else.
- **Server-side timeouts.** A client timeout that only closes its socket leaves the statement running, so an `UPDATE` can commit after the application reported a failure, and a migration queued for a lock holds every query behind it. PostgreSQL's own timeouts end the statement and roll it back. The client's read timeout is longer than the statement timeout so that PostgreSQL ends a slow statement and reports it before the client gives up. A client read timeout sends no cancel: it fires only when the server stopped answering, and crystal-pg 0.31.0 discards the backend key a cancel needs. The limits come from the environment: the client must know the statement timeout to wait past it, which rules out `ALTER ROLE … SET`, and psql refuses URL options. `migrate` has none so that `CREATE INDEX CONCURRENTLY` can finish.
- **Pool size from the environment.** How many requests a process serves at once is a deployment choice, bounded by the runtime role's connection limit and the server's `max_connections`, which only the operator knows.
- **Four spares in Cold Brew's pool.** A schedule block holds its connection until it commits with its lease, and `work` also gives the pool to Crema's recorder and console. With one spare, a long block starved maintenance and every other schedule each cycle. Maintenance, the recorder and the console each keep a connection, and two slots serve schedule blocks; a third due block waits. A fixed count keeps the budget independent of the schedule count. Rejected: a connection per schedule, whose budget grows with each `every`; releasing the lease before the block runs, which would let a failed block keep its lease.
- **A policy that applications can change.** The default stays strict, and the exception is written where the need is: a response that embeds a player allows that player and no other.
- **Copying from `default-src`.** A `-src` directive that is absent falls back to `default-src`. Writing only the new source would make it the whole list and block the origin's own requests: `add("connect-src", "https://api.example")` keeps `'self'`, which htmx needs.
- **`'none'` gives way.** `'none'` with another source is ignored by browsers, so adding to it would silently do nothing.
- **Validation.** A header built from strings is an injection point; the two patterns keep a value inside its directive, so a value cannot end a directive or start another.
- **Per-response nonces.** A nonce that repeats can be replayed. One per response, taken only when an action asks, leaves other responses with the strict default.
- **HSTS from `serve`, not the proxy.** The binary knows its environment, and a proxy that forgets the header leaves the site downgradable. Development and test use HTTP behind Latte, where a pinned HTTPS requirement would lock a browser out of every `*.caramel` host.
- **No `includeSubDomains` or `preload`.** A parent domain may serve sites that are not HTTPS-only, and a preload entry is hard to take back.
- **`.well-known` by name.** Allowing exactly that first segment keeps `.env`, `.git/` and `.well-known/.secret` unservable while serving what ACME and app-link files need.
- **Routing hidden paths.** A path that is not a served file is no different from any other unknown path, and an application may own such a route. Rejected: a hard 404 for hidden paths with only `.well-known` allowed, which would still block an application's own `/.something` route.
- **Streaming, not reading.** A large file does not sit in memory for each request.
- **`no-cache` unless versioned.** Assets are not fingerprinted yet, so `app.css` keeps its name while its content changes; `immutable` there would pin a stale file for a year. A name that carries a version never changes under that name. Rejected: `immutable` for every file.
- **No Range.** Assets are small and the proxy in front of `serve` is the place for ranges.
- Deferred: embedded and fingerprinted assets.
- Deferred: arm64 artifacts.
